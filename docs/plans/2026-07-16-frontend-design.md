## 〇、范围与全局约定

### 0.1 硬性约束（已采纳）

1. **单仓库（Monorepo）**，但两个前端应用（学生端 / 管理后台）**完全独立**：
   - 各自拥有独立文件夹、独立 `package.json`、独立 `node_modules`、独立 Tailwind/shadcn 配置。
   - **禁止**提取 `packages/ui` 或 `packages/shared` 公共包统一引用。
   - **禁止**跨项目 import（学生端不得引用管理端任何文件，反之亦然）。
   - 组件、hooks、工具函数全部在各自项目内自行设计。
2. **无需移动端适配**（两端均桌面优先，不做响应式移动布局）。
3. 学生端**课程列表页 / 课程详情页需做 SEO**。
4. 组件库按需自选，两端风格差异大，分别定制。
5. 认证：双 Token（Access + Refresh）、刷新令牌一次性旋转、登录记录表存 jti（不存 token 本身）、多端单设备、Token 黑名单、Redis 原子操作、Redis 异常降级 DB 且保原子性。

## 一、学生端设计

### 1.1 整体定位

**核心思路**：学生端不是一个"对话工具"，而是一个**在线教育课程平台**。学生来到这个网站的第一目的是**浏览和发现课程**，第二目的是**就感兴趣的课程进行 AI 咨询**。这与电商平台的"逛 → 看详情 → 咨询客服"的路径完全一致。

**设计隐喻**：电商展示型界面（Browsing-first）——首页展示推荐课程 → 课程列表可筛选搜索 → 课程详情页深度展示 → 点击"咨询"进入 AI 对话。

**风格基调**：
- 主风格：**Clean Tech + E-commerce Display** 融合。继承 Clean Tech 的清爽现代感，叠加电商的"内容即商品"展示密度。
- 气质：信任感、专业感、内容驱动。明亮开阔，大图大字，信息层级清晰。
- 页面节奏：首页/列表页 = 高视觉密度（课程卡片网格），详情页 = 中密度（结构化信息 + 图文混排），对话页 = 低密度（消息流 + 大留白）。
- Taste Skill 基线：DESIGN_VARIANCE ≈ 7（课程卡片可交错/Bento 网格），MOTION_INTENSITY ≈ 5（hover 微动 + 流式打字机），VISUAL_DENSITY ≈ 5（首页/列表偏高，对话页偏低）。
- **严禁**：Inter 字体、紫蓝 AI 发光、3 等宽卡片横排、纯黑、emoji、后台管理式侧边栏。

### 1.2 布局：顶部导航 + 全宽内容区

学生端**不设侧边栏**。全局使用顶部固定导航条（sticky header），下方为全宽内容区。各功能通过导航菜单入口跳转至独立页面，页面间职责清晰分离。

```
│  │  · 详情页：课程 Hero + Tab 内容 + 咨询 CTA                    │ │
```

**导航条设计细节**：
- 高度 64px，`sticky top-0 z-50`，`bg-white/95 backdrop-blur-sm border-b border-stone-200`
- 左侧：Logo（高度 32px）+ 品牌名
- 中间：导航链接组（首页 / 课程 / 会话 / 个人中心），当前页高亮：底部 teal-600 短下划线（2px, w-8）
- 右侧：用户头像（32px 圆）+ 下拉菜单（退出登录）
- 未登录态：右侧显示"登录"按钮，导航仅展示"首页"和"课程"
- 滚动行为：始终固定，不隐藏

### 1.3 配色系统

主强调色沿用 **Teal（青绿）**——与教育/成长品牌联想一致，同时区别于管理端的 Blue。中性色用 **Stone（暖灰）** 做背景，给内容展示以"自然光照"的观感。

```css

--text-muted:    #78716C;   /* stone-500 辅助文字/时间戳 */
--text-subtle:   #A8A29E;   /* stone-400 占位符/禁用文字 */
--brand:         #0D9488;   /* teal-600 主强调（按钮/链接/激活态/CTA） */
--brand-strong:  #0F766E;   /* teal-700 hover */
--brand-soft:    #CCFBF1;   /* teal-100 浅底（标签/选中态） */
```

> 60-30-10：stone 背景和表面 60%，文字/边框 30%，teal 强调 10%。课程卡片封面图/缩略图是彩色，天然提供视觉丰富度，无需额外的装饰色。

### 1.4 字体系统

- **拉丁/数字显示**：`Outfit`（几何现代，非 Inter，与 Taste Skill 要求一致）

- **等宽（代码块/时间戳）**：`Geist Mono`

| 事件 | 前端渲染动作 |

| `error` | 消息末尾显示 ErrorBanner + 错误信息 |
| `end` | 标记消息完成，启用 FeedbackBar |
| `:heartbeat` | 重置超时计时器（30s 无消息则断连提示） |

## 二、老师后台管理端设计

### 2.1 整体定位

管理端是**知识库运维 + 运营管理工具**，面向的是有明确任务目标的老师/超管。设计以"效率优先、信息密度高、操作路径短"为核心。

- Taste Skill 基线：DESIGN_VARIANCE ≈ 4（可预测网格），MOTION_INTENSITY ≈ 3（仅 hover/active，无 perpetual 动画），VISUAL_DENSITY ≈ 8（cockpit：1px 分隔线、mono 数字、极少卡片、密集行）。

**批量修正工作流（核心操作）**：
1. 默认筛选 `correction_status=PENDING`
2. 老师勾选 N 个 chunk → 点击"批量修正"
3. 弹出 Dialog：
   - 设置 `collection_type`：下拉（TECHNICAL_QA / COURSE_INFO）
   - 设置 `course_id`：课程搜索选择器（搜索课程名，选后填入 course_id）
   - [确认] 按钮
4. 确认后调 `POST /api/v1/admin/chunks/batch-update`（不改 content，不重新向量化）
5. 成功后，那些 chunk 的 `collection_type` / `course_id` 在界面上即时更新
6. 老师再勾选 + 点击"标记已修正" → 调 `POST /api/v1/admin/chunks/batch-corrected`
7. `correction_status` 变为 `CORRECTED`，Badge 从 amber 变 emerald

**编辑单个分片内容**：
- 点击行末"编辑"按钮 → 右侧滑出 `Sheet`（Drawer，宽 600px）
- 内容区：`textarea` 显示完整 chunk 文本（等宽字体，`min-h-[400px]`）
- 下方显示元数据：文档名、heading_path、char_offset、token_count（只读）
- [保存] 按钮 → 调 `PUT /api/v1/admin/chunks/{id}`（改 content → 重新向量化）
- 保存后提示"内容已更新，正在重新向量化…"

## 三、登录模块设计

### 3.1 概述

两个端有**两套独立的登录页**——学生端登录页和管理端登录页布局不同、风格不同、路由不同，但共享同一套后端认证 API。登录后的跳转目标也不同（学生端 → 首页、管理端 → 仪表盘）。

### 3.4 认证机制（双 Token）

以下内容基于后端已设计的认证体系，从**前端视角**描述实现细节。

#### 3.4.1 Token 生命周期

| Token | 有效期 | 存储位置 | 用途 |
|-------|--------|---------|------|
| Access Token | 15 min | 内存（JS 变量）+ `httpOnly` cookie（可选） | 每请求携带 Authorization header |
| Refresh Token | 7 d / 30 d（记住此设备） | **仅 `httpOnly` cookie** | 静默刷新 AT |

> 安全决策：RT 仅存 `httpOnly` cookie（`Secure; HttpOnly; SameSite=Strict; Path=/api/auth`），JS 完全无法访问，XSS 无法窃取。AT 存内存变量 + 可选的 `httpOnly` cookie 双通道。

#### 3.4.2 前端认证流程

**登录**：
```
1. POST /api/v1/auth/login { email, password, deviceType: "WEB_DESKTOP", rememberMe }
2. 成功 → 响应体含 { accessToken, expiresIn }
3. 将 accessToken 存入内存变量
4. RT 由后端 Set-Cookie 自动写入（前端无需处理）
5. 跳转目标页
```

**每请求携带 AT**：
```
fetch(url, {
  headers: { 'Authorization': `Bearer ${accessToken}` }
})
```
统一封装在 API client（`lib/api.ts`）的请求拦截器中。

**静默刷新**：
- 设置定时器：AT 过期前 2 分钟自动调 `POST /api/v1/auth/refresh`
- 或：请求收到 401 → 拦截器自动调 refresh → 成功则重放原请求 → 失败则跳转登录页
- refresh 请求不需要传 body（RT 在 cookie 中），后端返回新的 `{ accessToken, expiresIn }`
- 更新内存中的 AT，重启定时器

**并发请求去重**：
- 多个请求同时触发 401 时，只发一次 refresh，其余请求排队等待
- 实现：维护一个 `refreshPromise` 全局变量，首个 401 发起 refresh 时赋值，后续 401 await 该 promise

**登出**：
```
1. POST /api/v1/auth/logout
2. 后端将当前 AT jti + RT jti 加入黑名单，清除 httpOnly cookie
3. 前端清除内存 AT，跳转登录页
```

**被踢出（单设备策略，Redis 驱动）**：
- 用户在设备 A 已登录，在设备 B 登录同一账号
- 后端执行 Redis Lua 脚本 `kick_and_login`：原子完成"覆盖活跃设备指针 + 旧设备 jti 入 Redis 黑名单"
- PG 异步落盘审计记录（INSERT 新记录 + UPDATE 旧记录 REVOKED + INSERT 黑名单）
- 设备 A 下次请求时，AT 校验命中 Redis 黑名单 → 401 + `error_code: DEVICE_KICKED`
- 前端拦截器检测到 `DEVICE_KICKED` → 显示 Toast "您已在其他设备登录，请重新登录" → 跳转登录页
- **旧设备失效延迟**：纳秒级（Redis Lua 内同步完成黑名单写入），无 PG 写入窗口

#### 3.4.3 AuthProvider（React Context）

```ts
// 核心接口（学生端和管理端各有一套独立实现）
interface AuthState {
  user: User | null;
  accessToken: string | null;
  isAuthenticated: boolean;
  isLoading: boolean;       // 初始加载中（刷新 token 阶段）
}

interface AuthContextValue extends AuthState {
  login: (email: string, password: string, rememberMe?: boolean) => Promise<void>;
  logout: () => Promise<void>;
  refreshToken: () => Promise<string | null>;
}
```

**初始化流程**：
1. App 启动 → AuthProvider mount → `isLoading = true`
2. 尝试 `POST /api/v1/auth/refresh`（cookie 自动携带 RT）
3. 成功 → 拿到 AT + user info → `isAuthenticated = true`
4. 失败 → `isAuthenticated = false`（无需跳转，允许浏览公开页面）
5. `isLoading = false`

#### 3.4.4 路由保护

**学生端中间件**（`student-frontend/src/middleware.ts`）：
- 公开路由（无需登录）：`/`, `/courses`, `/courses/[id]`, `/login`
- 受保护路由（需要登录）：`/chat`, `/sessions`, `/profile`
- 未登录访问受保护路由 → redirect to `/login?redirect={originalUrl}`
- 登录后重定向回 `redirect` 参数指定的 URL

**管理端中间件**（`frontend/src/middleware.ts`）：
- 公开路由：`/login` 仅此一个
- 所有其他路由需要登录 + 角色校验
- 未登录 → redirect to `/login`
- 已登录但角色非 TEACHER/SUPER_ADMIN → 显示 403 或 redirect to `/login?error=unauthorized`

### 3.5 错误处理 & 用户体验

| 场景 | 前端处理 |
|------|---------|
| AT 过期 + RT 有效 | 静默刷新，用户无感知（loading spinner 最多 1s） |
| AT 过期 + RT 过期 | 跳转登录页，Toast "登录已过期，请重新登录" |
| RT 复用（安全攻击） | 后端返回 401 + 特定 error code → Toast "检测到异常登录，已强制下线" → 跳转登录页 |
| 网络错误 | Toast "网络连接失败，请检查网络后重试"，不跳转登录页（保留当前页面状态） |
| 429 限流 | Toast "操作太频繁，请稍后再试" |
| 账号被禁用 | Toast "账号已被管理员禁用"，跳转登录页 |
| 被踢出 | 后端返回 401 + `error_code: DEVICE_KICKED`（Redis 黑名单命中）→ Toast "您的账号在其他设备登录" → 跳转登录页 |
| Redis 降级 | 用户无感知。后端降级为 PG 事务校验，响应略慢但功能正常；Redis 恢复后自动回切 |

## 四、SEO 优化方案（学生端课程页）

仅**课程列表页**（`/courses`）和**课程详情页**（`/courses/[id]`）做 SEO，其余页面均为登录后私有内容。

| 手段 | 详细实现 |
|------|---------|
| **渲染策略** | 课程列表/详情页用 Server Component + ISR（`revalidate = 3600`）。老师新增/更新课程时调 `revalidatePath` 或 `revalidateTag('courses')` 按需再生 |
| **Dynamic Metadata** | `generateMetadata({ params, searchParams })`：title = "{课程名} - {平台名}" 或 "{分类}课程列表"，description 取课程简述前 160 字符，openGraph.image = 课程封面 URL |
| **结构化数据** | JSON-LD 注入：`Course` schema（name, provider, description, instructor, offers.price, hasCourseInstance.startDate, educationalLevel）、`BreadcrumbList`、`ItemList`（列表页） |
| **Sitemap** | `app/sitemap.ts`：动态生成课程 URL（`lastModified` 取 `updated_at`，`changefreq='daily'`，`priority=0.8`） |
| **robots.txt** | `app/robots.ts`：Allow `/courses`，Disallow `/chat`, `/sessions`, `/profile`, `/api` |
| **语义 HTML** | `<html lang="zh-CN">`；`<article>` 包裹课程详情；`<h1>` 仅课程名；`<img alt>` 用真实课程名；`<time>` 标注课程更新日期 |
| **性能** | 封面图用 `next/image` + MinIO remote loader + `priority`（首屏）、`loading="lazy"`（非首屏）；字体 `display=swap` 自托管 |
