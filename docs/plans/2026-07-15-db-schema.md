## 通用约定

| 规则 | 说明 |
|------|------|
| **主键策略** | 所有表统一 `id BIGINT`，雪花算法（应用层生成，DB 不自增） |
| **软删除** | 所有表统一 `deleted BIGINT DEFAULT 0`；`0` = 未删除，非 0 = 删除时的时间戳（毫秒） |
| **时间戳** | 统一 `TIMESTAMPTZ DEFAULT now()` |
| **命名规范** | 表名/列名 snake_case；FK 命名为 `{关联表}_id`；索引 `idx_{表名}_{列名}` / `uniq_{表名}_{列名}` |
| **索引策略** | 优先条件索引（`WHERE deleted = 0`）、唯一索引、联合索引；遵循最左前缀原则 |
| **course_id 约定** | VARCHAR(64)，`'DEFAULT'` = 通用内容（所有学生可见），具体值 = 课程专属（仅选课学生可见） |

## 一、B 端知识库管理

### 知识库与文档关系

```
┌──────────────────┐ 1    N ┌──────────────────┐ 1    N ┌─────────────────────┐
│  knowledge_base  │────────│     document     │────────│   document_chunk    │
│  (知识库容器)    │        │   (文档元信息)    │        │  (分片+collection   │
│                  │        │                  │        │   _type 标记)        │
└──────────────────┘        └──────────────────┘        └─────────────────────┘
        │                           │                              │
        └─ 容器，不区分类型          └─ 原始元数据提取              └─ chunk 级别标记：
                                                                   ├─ collection_type
                                                                   │   TECHNICAL_QA / COURSE_INFO
                                                                   └─ course_id
                                                                       'DEFAULT' / 具体课程 ID
```

**设计要点：**
- 知识库只是文档的容器，本身不区分 collection_type
- 检索类型在 chunk 级别区分——同一文档的不同 chunk 可以属于不同 collection_type
- 权限通过 `course_id` 值控制：`'DEFAULT'` = 通用，具体值 = 课程专属

### 5. `sys_login_record` — 登录记录（会话注册表）

**单设备互踢流程（Redis 驱动 + PG 审计）**：

> **设计原则**：Redis 是执法层（纳秒级生效），PG 是审计层（持久化记录）。Redis Lua 脚本原子完成"覆盖活跃设备 + 旧 jti 入黑名单"，PG 异步落盘记录操作轨迹。

```
用户 B 在设备 B 登录
  │
  ├─ 1. 生成新 jti_at, jti_rt, login_id
  │
  ├─ 2. 执行 Redis Lua 脚本 kick_and_login（原子操作）
  │      ├─ GET auth:cur:{userId}:{deviceType}  → 拿到旧设备 jti
  │      ├─ SET auth:cur:{userId}:{deviceType} = "new_jti_at|new_jti_rt|new_loginId"
  │      └─ IF 旧设备存在:
  │           SETEX auth:bl:{old_jti_at} {AT剩余TTL} "DEVICE_KICKED|{timestamp}"
  │           SETEX auth:bl:{old_jti_rt} {RT剩余TTL} "DEVICE_KICKED|{timestamp}"
  │      → 返回 { kicked: true/false, old_jti_at, old_jti_rt }
  │
  ├─ 3. PG 落盘（异步/非阻塞，失败可重试，不影响安全性）
  │      ├─ INSERT sys_login_record（新记录，status=ACTIVE）
  │      ├─ IF kicked: UPDATE 旧 sys_login_record → status=REVOKED
  │      └─ IF kicked: INSERT sys_token_blacklist（旧 jti_at + jti_rt, reason=DEVICE_KICKED）
  │
  └─ 4. 签发新 Token → 返回给用户 B

  ── 同时，设备 A 的下一个请求 ──
  │
  ├─ 校验 AT: EXISTS auth:bl:{old_jti_at} → 命中 → 403
  └─ 刷新 RT: EXISTS auth:bl:{old_jti_rt} → 命中 → 401
```

**Redis 数据结构设计**：

| Key | Type | TTL | 用途 |
|-----|------|-----|------|
| `auth:cur:{userId}:{deviceType}` | String | = RT 有效期 | 当前活跃设备指针，value="jti_at\|jti_rt\|loginId" |
| `auth:bl:{jti}` | String | = Token 剩余有效期 | 黑名单标记，value="reason\|timestamp" |
| `auth:rt:used:{jti_rt}` | String | = RT 剩余有效期 | RT 一次性标记（复用检测） |

**核心 Lua 脚本：`kick_and_login.lua`**：

```lua
-- KEYS[1] = auth:cur:{userId}:{deviceType}
-- ARGV[1] = new_jti_at|new_jti_rt|new_login_id（新设备标记）
-- ARGV[2] = cur_key_ttl（= 新 RT 有效期，秒）
-- ARGV[3] = old_at_ttl（旧 AT 剩余有效期，秒，无旧设备时传 0）
-- ARGV[4] = old_rt_ttl（旧 RT 剩余有效期，秒，无旧设备时传 0）
-- ARGV[5] = kick_reason（"DEVICE_KICKED"）
-- ARGV[6] = current_timestamp（由 Java 传入，避免 Lua 内调 TIME 导致脚本不可复制）

-- 1. 获取旧设备信息
local old = redis.call('GET', KEYS[1])

-- 2. 写入新设备标记（覆盖旧设备）
redis.call('SETEX', KEYS[1], tonumber(ARGV[2]), ARGV[1])

-- 3. 如果存在旧设备，将其 jti 加入黑名单
local kicked = false
local old_jti_at = ''
local old_jti_rt = ''

if old and old ~= '' then
    -- 解析 "jti_at|jti_rt|loginId"
    local parts = {}
    for part in string.gmatch(old, '[^|]+') do
        table.insert(parts, part)
    end
    old_jti_at = parts[1] or ''
    old_jti_rt = parts[2] or ''

    if old_jti_at ~= '' and tonumber(ARGV[3]) > 0 then
        redis.call('SETEX', 'auth:bl:' .. old_jti_at, tonumber(ARGV[3]),
                   ARGV[5] .. '|' .. ARGV[6])
    end
    if old_jti_rt ~= '' and tonumber(ARGV[4]) > 0 then
        redis.call('SETEX', 'auth:bl:' .. old_jti_rt, tonumber(ARGV[4]),
                   ARGV[5] .. '|' .. ARGV[6])
    end
    kicked = true
end

return cjson.encode({
    kicked = kicked,
    old_jti_at = old_jti_at,
    old_jti_rt = old_jti_rt
})
```

**Redis 降级 PG 策略**：

当 Redis 不可用时，降级为纯 PG 事务（保证原子性但响应变慢）：

```
BEGIN;
  -- 行锁：锁定该用户+设备类型的活跃记录
  SELECT id, jti_at, jti_rt FROM sys_login_record
    WHERE user_id = ? AND device_type = ? AND status = 'ACTIVE' AND deleted = 0
    FOR UPDATE;

  -- 如果有旧记录：标记 REVOKED + 写黑名单
  UPDATE sys_login_record SET status = 'REVOKED', updated_at = now()
    WHERE user_id = ? AND device_type = ? AND status = 'ACTIVE' AND deleted = 0;

  INSERT INTO sys_token_blacklist (jti, token_type, user_id, reason, expires_at) VALUES ...;

  -- 插入新记录
  INSERT INTO sys_login_record (...) VALUES (...);
COMMIT;
```

**降级期间注意事项**：
- 降级时旧设备失效有 PG 写入延迟（毫秒级），但 `FOR UPDATE` 行锁保证了不会有并发窗口
- Redis 恢复后，启动同步任务将 PG 黑名单回填到 Redis（`auth:bl:{jti}`）
- 降级期间 Token 校验直接查 PG（`SELECT 1 FROM sys_token_blacklist WHERE jti = ? AND deleted = 0`）

**清理策略**：定时任务删除 `expires_at < now()` 的记录（软删除，保留审计）。

### 6. `sys_token_blacklist` — Token 黑名单

**定位**：存储已被吊销的单个 Token jti。管理员禁用某 Token 或用户后立即生效。

| 列 | 类型 | 约束 | 说明 |
|---|------|------|------|
| id | BIGINT | PK | 雪花算法 |
| jti | VARCHAR(64) | NOT NULL | 被禁 Token 的 JWT ID（AT 或 RT） |
| token_type | VARCHAR(10) | NOT NULL | ACCESS / REFRESH |
| user_id | BIGINT | FK → sys_user NOT NULL | 所属用户 |
| blacklisted_by | BIGINT | FK → sys_user | 操作人（SUPER_ADMIN / TEACHER） |
| reason | VARCHAR(200) | | 禁用原因（DEVICE_KICKED / USER_DISABLED / MANUAL_REVOKE / TOKEN_REUSE） |
| expires_at | TIMESTAMPTZ | NOT NULL | 该 jti 对应 Token 的原始过期时间（过期后可清理此条记录） |
| deleted | BIGINT | DEFAULT 0 | |
| created_at | TIMESTAMPTZ | DEFAULT now() | |

**索引：**

```sql
-- Token 校验时查黑名单（最高频，每个请求都要查）

-- 按用户查所有被禁 Token

-- 定时清理过期黑名单
CREATE INDEX idx_token_blacklist_expires ON sys_token_blacklist(expires_at) WHERE deleted = 0;
```

**黑名单写入场景（Redis 执法 + PG 审计）**：

> 所有黑名单写入**先写 Redis**（`SETEX auth:bl:{jti} {ttl} "reason|timestamp"`），再异步落盘 PG。Redis 失败时降级为 PG 事务。

| 场景 | Redis 操作（执法层） | PG 操作（审计层） |
|------|---------------------|-------------------|
| 单设备互踢 | Lua 脚本内 `SETEX auth:bl:{old_jti}` | INSERT sys_token_blacklist + UPDATE sys_login_record REVOKED |
| 管理员禁用用户 | `SADD auth:bl:batch` + 逐个 `SETEX auth:bl:{jti}` | 批量 INSERT sys_token_blacklist + 批量 UPDATE sys_login_record REVOKED |
| 管理员禁用单个 Token | `SETEX auth:bl:{jti}` | INSERT sys_token_blacklist |
| RT 复用检测 | `SETEX auth:bl:{old_jti_rt}` + 该用户所有 jti 批量 `SETEX` | 批量 INSERT + 批量 UPDATE |
| 用户主动登出 | `SETEX auth:bl:{jti_at}` + `SETEX auth:bl:{jti_rt}` | INSERT sys_token_blacklist + UPDATE sys_login_record REVOKED |

**管理员禁用用户 Lua 脚本：`disable_user.lua`**：

```lua
-- KEYS[1] = auth:disable:{userId}  (防重入标记)
-- ARGV[1] = userId
-- ARGV[2] = adminUserId
-- ARGV[3] = reason ("USER_DISABLED")
-- ARGV[4] = timestamp
-- ARGV[5..n] = jti_list (该用户所有 ACTIVE 的 jti_at 和 jti_rt，交替排列: at1,rt1,at2,rt2,...)
-- ARGV[6..n] = ttl_list (对应每个 jti 的剩余 TTL)

local disabled = redis.call('SET', KEYS[1], '1', 'NX', 'EX', 300)  -- 5min 防重入
if not disabled then return 'ALREADY_PROCESSING' end

local count = 0
local jti_count = (#ARGV - 5) / 2 + 1

for i = 1, jti_count do
    local jti = ARGV[5 + (i - 1) * 2]
    local ttl = tonumber(ARGV[6 + (i - 1) * 2])
    if jti and jti ~= '' and ttl and ttl > 0 then
        redis.call('SETEX', 'auth:bl:' .. jti, ttl, ARGV[3] .. '|' .. ARGV[4])
        count = count + 1
    end
end

-- 同时清除活跃设备指针（所有 device_type）
-- 由 Java 层遍历 device_type 列表，逐个 DEL auth:cur:{userId}:{deviceType}

return cjson.encode({ disabled_jti_count = count })
```

**校验流程（每个请求）**：
```
1. 从 Authorization header 提取 AT，解析 payload 拿 jti
2. 查 Redis: EXISTS auth:bl:{jti}（热路径，O(1)）
3. Redis 命中 → 403
4. Redis 未命中 / Redis 不可用 → 降级查 PG:
   SELECT 1 FROM sys_token_blacklist WHERE jti = ? AND deleted = 0
5. PG 命中 → 403（同时异步回写 Redis）
6. 通过 → 继续业务逻辑
```

**清理策略**：定时任务删除 `expires_at < now()` 的黑名单记录。Token 过期后黑名单保留无意义。

## Milvus 单一 Collection 设计（v4 核心）

> **单一 Collection `knowledge_chunks`**，通过 `collection_type` 字段过滤区分两类检索。

```sql
-- Milvus Collection Schema（单一 Collection）
Collection: knowledge_chunks

字段：
  - chunk_id (VARCHAR, PK, max_length=64)
  - doc_id (VARCHAR, max_length=64)
  - kb_id (VARCHAR, max_length=64)
  - content (VARCHAR, max_length=65535)         -- 截断版，完整版在 PG
  - heading_path (VARCHAR, max_length=500)
  - dense_vector (FLOAT_VECTOR, dim=1024)       -- text-embedding-v4
  - sparse_vector (SPARSE_FLOAT_VECTOR)         -- BM25 (Milvus 2.5 chinese analyzer)
  - chunk_index (INT32)
  - token_count (INT32)
  - collection_type (VARCHAR, max_length=20)     ← 关键过滤字段：TECHNICAL_QA / COURSE_INFO
  - course_id (VARCHAR, max_length=64)          ← 关键过滤字段：'DEFAULT' / 具体课程 ID
  - updated_at (INT64)

索引：
  - dense_vector: HNSW, COSINE, M=16, efConstruction=200
  - sparse_vector: SPARSE_INVERTED_INDEX, BM25, IP
  - collection_type: 标量索引（加速过滤）
  - course_id: 标量索引（加速过滤）
```

**检索时过滤表达式：**

```
// 学生检索时，先查 course_enrollment 拿到所选课程 ID 列表（转为字符串）
// 然后在 Milvus 中按 collection_type + course_id 过滤：

// TECHNICAL_QA 检索（技术答疑）
collection_type == 'TECHNICAL_QA' 
  AND (course_id == 'DEFAULT' OR course_id IN ['已选课程ID1', '已选课程ID2', ...])

// COURSE_INFO 检索（课程咨询）
collection_type == 'COURSE_INFO'
  AND (course_id == 'DEFAULT' OR course_id IN ['已选课程ID1', '已选课程ID2', ...])
```

## 递归文档提取流程（v4 保留）

```
文档上传 → ETL Pipeline
  ↓
① Tika 解析：提取全文 + 原始 metadata（PDF Info Dictionary）
  ↓
② 递归分片（Recursive Chunking）：
   - 优先按章节分隔符切分（## / ###）
   - 章节超长时按段落 → 句子递归切分
   - chunk-size=768 tokens, overlap=128 tokens
   - 每个 chunk 记录：
     * heading_path（章节路径）
     * parent_chunk_id（父级 chunk，用于上下文展开）
     * prev_chunk_id / next_chunk_id（兄弟 chunk，用于相邻合并）
     * char_offset_start / char_offset_end（原文偏移，精确定位）
  ↓
③ 标记 collection_type + course_id：
   - 默认全部 collection_type='TECHNICAL_QA', course_id='DEFAULT'（或上传时指定课程的值）
   - correction_status='PENDING'（待 B 端批量修正）
   - 不自动分类——B 端审核界面批量修正 collection_type / course_id
  ↓
④ 写入 PG document_chunk 表
  ↓
⑤ Embedding（text-embedding-v4, 1024 维）+ BM25 Sparse 向量化
   - dense_vector 同时写入 PG（冗余存储）+ Milvus
  ↓
⑥ 写入 Milvus 单一 Collection（含 collection_type + course_id 过滤字段）
```

## ETL 异步链路设计（旁路修正式）

### 异步状态机

```
上传 API（同步返回 doc_id）
  │  document.parse_status = 'PENDING'
  │
  ▼
@Async("etlExecutor") processDocument(docId)
  │
  ├─ PARSING ──── Tika 解析：提取全文 + 原始 metadata
  │              document.parse_status = 'PARSING' → 'PARSED'
  │
  ├─ CHUNKING ─── 递归分片：chunk-size=768, overlap=128
  │              document.parse_status = 'CHUNKING' → 'CHUNKED'
  │              每个 chunk: correction_status='PENDING'
  │              collection_type='TECHNICAL_QA'（默认）
  │              course_id='DEFAULT' 或上传时指定值
  │
  ├─ EMBEDDING ── text-embedding-v4 向量化 + 存 PG dense_vector
  │              document.parse_status = 'EMBEDDING'
  │
  └─ INDEXED ──── 写入 Milvus（dense_vector + 标量字段）
                 document.parse_status = 'INDEXED'
                 ← 知识库立即可用，不阻断

异常 → document.parse_status = 'FAILED' + error_message
```

### 各阶段可自动提取 vs 需后续补充

| 阶段 | 能自动提取 | 提取不到 / 需后续人工补充 |
|------|-----------|-------------------------|
| **上传** | file_type, file_size, kb_id, 原始文件名→title 候选 | 文档的业务含义；正确中文标题（文件名可能乱码或无意义） |
| **解析（Tika）** | 全文文本、PDF Info Dictionary（作者/主题/关键词/创建时间）、大纲/目录/标题层级、总页数 | 图片中的文字（无 OCR）；表格结构语义；图表信息；公式/数学符号 |
| **分片** | heading_path、char_offset_start/end、parent/prev/next_chunk_id、token_count、chunk_index、start/end_page | 分片边界是否语义完整（算法可能切断算法描述/代码块/表格行） |
| **分类标记** | course_id（上传时指定则继承，未指定='DEFAULT'） | **collection_type**：同一文档不同章节可能分属不同类型，机器无法准确判断；课程介绍中夹杂的技术内容归属模糊 |
| **向量化** | dense_vector（text-embedding-v4）、sparse_vector（Milvus BM25 自动生成） | — |

### 旁路修正策略

- Pipeline 一次性跑完到 INDEXED，知识库立即可检索
- 所有 chunk 默认 `correction_status = 'PENDING'`
- B 端审核界面按 `correction_status = 'PENDING'` 筛选，批量修正
- 修正完成后标记 `correction_status = 'CORRECTED'`
- 修正过程中知识库始终可用（旁路，不阻断 C 端检索）

## Milvus upsert / 重新向量化策略

### 核心规则：修正原数据后是否需要重新向量化？

| 修正操作 | 是否需要重新向量化 | 原因 |
|---------|:--:|------|
| 改 `collection_type` | **否** | 标量字段，与向量无关 |
| 改 `course_id` | **否** | 标量字段，与向量无关 |
| 改 `content`（chunk 文本） | **是** | dense_vector 从 content 生成，content 变则向量 stale |

### Milvus upsert 实现：PG 冗余 dense_vector

Milvus 的 `upsert` 是 **delete-then-insert**——即使只改标量字段，也必须提供完整记录（含 dense_vector）。

**方案：PG `document_chunk.dense_vector` (BYTEA) 冗余存储**

| 好处 | 说明 |
|------|------|
| 批量修正免回查 | 改 collection_type/course_id 时，直接从 PG 读 dense_vector 构造 upsert 请求，不需要回查 Milvus |
| Milvus 重建 | 万一 Milvus 数据丢失/需重建索引，可直接从 PG 批量灌入，不需要重新跑 embedding API |
| 存储开销可忽略 | 1024 floats = 4KB/chunk，1 万条 = 40MB |

### B 端修正工作流

```
① 筛选 PENDING chunks（按 kb_id / doc_id 过滤）
    ↓
② 批量改 collection_type / course_id（不需要重新向量化）
    → 更新 PG 标量字段
    → 从 PG 读 dense_vector → 构造 Milvus upsert → 批量提交
    → 不调 embedding API
    ↓
③ （可选）单个改 content（需要重新向量化）
    → 调 text-embedding-v4 重新生成 dense_vector
    → 更新 PG dense_vector + content
    → 更新 Milvus dense_vector + content（sparse 自动重算）
    ↓
④ 批量标记 correction_status = 'CORRECTED'
```

## MyBatis-Plus 配置要点

```yaml
mybatis-plus:
  global-config:
    db-config:
      logic-delete-field: deleted
      logic-not-delete-value: "0"
  # 雪花算法配置
  worker-id: 1       # 工作机器 ID（多实例需唯一）
  datacenter-id: 1   # 数据中心 ID
```

**软删除方案**：MP 默认只支持 Integer 0/1，`BIGINT` 存时间戳建议在 Service 层手动 SQL：

```java
UPDATE course_info SET deleted = #{timestamp} WHERE id = #{id};
```

所有查询 SQL 在 WHERE 统一带 `AND deleted = 0`。

**雪花算法配置**：应用启动时从 `sys_node` 表（或 Redis）获取 worker-id，保证多实例唯一。

### CRUD 接口实现规范

**统一响应格式：**

```java
record PageResponse<T>(List<T> records, long total, int page, int size) {}
record ApiResponse<T>(int code, String message, T data) {
    static <T> ApiResponse<T> ok(T data) { return new ApiResponse<>(0, "success", data); }
    static ApiResponse<Void> ok() { return new ApiResponse<>(0, "success", null); }
}
```

**软删除实现：**

```java
// 所有 Service 层删除操作统一走：
UPDATE {table} SET deleted = #{timestamp} WHERE id = #{id};

// 级联软删示例：删除知识库时
UPDATE knowledge_base SET deleted = #{ts} WHERE id = #{kbId};
UPDATE document SET deleted = #{ts} WHERE kb_id = #{kbId} AND deleted = 0;
UPDATE document_chunk SET deleted = #{ts} WHERE kb_id = #{kbId} AND deleted = 0;
// 同时调用 MilvusStore.deleteByKbId(kbId) 删除向量
```

**权限校验：**

```java
@PreAuthorize("hasAnyRole('SUPER_ADMIN', 'TEACHER')")
@GetMapping("/admin/users")
public ApiResponse<PageResponse<UserDTO>> list(...) { ... }

// 老师只能操作自己创建的资源（Service 层校验）
public void deleteCourse(Long courseId, Long currentUserId) {
    CourseInfo course = courseRepo.findById(courseId)
        .orElseThrow(() -> new NotFoundException("课程不存在"));
    if (!currentUser.isSuperAdmin() && !course.getCreatedBy().equals(currentUserId)) {
        throw new ForbiddenException("无权操作此课程");
    }
    course.setDeleted(System.currentTimeMillis());
    courseRepo.save(course);
}
```
