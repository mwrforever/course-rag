## P2-1. 附件文档逐块串行 embedding，未用批量接口

- 档位：高置信可落地
- 位置：`backend/src/main/java/com/commerce/rag/service/AttachmentDocumentProcessor.java:126-131`（调用方关键路径：`worker/ChatRequestWorker.java:384`）

现状代码：

```java
// AttachmentDocumentProcessor.doProcess（缓存未命中时执行，位于对话 run 主路径）
// 3. 逐块向量化（embed(String) 返回 float[]，Spring AI 1.1.2 便利方法）
List<DocumentLocalChunk> chunks = new ArrayList<>(pieces.size());
for (int i = 0; i < pieces.size(); i++) {
    float[] vector = embeddingModel.embed(pieces.get(i));   // ← 每块一次远程 HTTP，串行
    if (vector != null && vector.length > 0) {
        chunks.add(new DocumentLocalChunk(pieces.get(i), vector, i));
    }
}
```

问题分析：附件文档处理在 `ChatRequestWorker.processRequest` 内同步执行（构建图输入、SSE 首个
metadata 事件之前），是**对话关键路径**。文档附件上限 50MB（application.yml
`attachment.document-max-size-mb: 50`），按 768 token/块切分可达数百块；每块一次
DashScope embedding 远程调用（单次数百 ms），首次上传的大 PDF 附件 = 数百次串行远程调用，
耗时数十秒到分钟级，期间 runPool worker 线程被占、学生端 SSE 一直收不到首事件。
Caffeine 缓存（`AttachmentCacheService`，30min TTL）只对**同字节 hash 重复出现**生效，
首次处理必须全价支付。对照：ETL 主链路 08-16 H-3 已批量化（`EtlPipeline.java:524-529`
`embeddingModel.embed(List)` + `etl.embedding-batch-size: 16`），附件处理器是同模式的漏网之地，
且它在比 ETL（离线）敏感得多的交互路径上。

优化方案：与 ETL H-3 完全同款——分批调用批量接口，按需保留空向量降级语义：

```java
// 建议形态（伪代码）：批量 embedding，批大小复用 etl.embedding-batch-size 配置
for (int start = 0; start < pieces.size(); start += batchSize) {
    List<String> batch = pieces.subList(start, Math.min(start + batchSize, pieces.size()));
    List<float[]> vectors = embeddingModel.embed(batch);   // 一次请求携带多条文本
    for (int i = 0; i < batch.size(); i++) {
        if (vectors.get(i) != null && vectors.get(i).length > 0) {
            chunks.add(new DocumentLocalChunk(batch.get(i), vectors.get(i), start + i));
        }
    }
}
```

预期收益：远程调用次数从 N 降为 N/16；200 块大文档附件处理从约 200 次串行 HTTP
（约 60s 量级）降为约 13 次批量调用（秒级~十余秒），首 token 延迟同步下降。
失败语义不变（单批失败整批跳过，与现状逐块失败跳过粒度差异可接受——ETL 已按该粒度运行）。

风险与一致性影响：低。DashScope embedding 批量接口已在 ETL 链路生产验证（H-3 实施即用）；
分片顺序由下标保持；空向量过滤逻辑等价。需同步调整该类单测（mock embed(String) 改 embed(List)）。

## P2-2. 附件下载/图片 caption 全串行，违反宪法「附件批处理用 CompletableFuture」

- 档位：高置信可落地
- 位置：
  - `backend/src/main/java/com/commerce/rag/service/AttachmentOrchestrator.java:57-72`（附件级串行：下载→处理）
  - `backend/src/main/java/com/commerce/rag/service/AttachmentImageProcessor.java:50-67`（图片 caption 循环串行）
  - `backend/src/main/java/com/commerce/rag/etl/EtlPipeline.java:325-346,395-429`（ETL 图片逐张 upload+caption 串行）

现状代码：

```java
// AttachmentOrchestrator.process：多附件逐个「下载 → 处理」，全串行
for (AttachmentRecord att : attachments) {
    byte[] bytes = attachmentService.download(att.url());          // ← MinIO 远程下载，串行
    if ("image".equals(att.type())) { ... } else {
        documents.put(att.url(), documentProcessor.processDocument(bytes, att.name())); // ← 内含逐块 embed（P2-1）
    }
}

// AttachmentImageProcessor.processImages：图片 caption 循环内逐张 VLM 调用
for (int i = 0; i < images.size(); i++) {
    String caption = cacheService.getOrProcess(hash, b -> captionInternal(b, name), bytes); // ← VLM 1~3s/张，串行
}

// EtlPipeline.buildImageChunk：每张图「MinIO 上传 + VLM caption」串行，图与图之间也串行
String objectKey = uploadImage(doc, image);                        // ← MinIO 上传
String caption = imageCaptionService.caption(image.bytes(), ...);  // ← VLM，串行
```

问题分析：附件上限 10 个/消息（`attachment.max-count: 10`）。当前一条多附件消息在
runPool worker 线程上的处理时长 = Σ(每附件下载) + Σ(文档逐块 embed) + Σ(图片 VLM caption)
——全部串行叠加在 SSE 首 token 之前。典型场景「2 个 PDF + 3 张图」：2 次 MinIO 下载串行 +
数百次 embed 串行 + 3 次 VLM（1~3s/张）串行。工程宪法（AGENTS.md「并发与异步」）明文要求
「并行场景用 CompletableFuture（多查询检索、**附件批处理**）」——检索侧（SearchKnowledgeTool/
RetrieveNode）已遵守，附件侧（Task 4~7 实现）未落实。ETL 侧图片处理同理：图片密集 PDF
（几十张图）chunking 阶段 = 几十次串行 MinIO 上传 + 几十次串行 VLM 调用，分钟级。

优化方案（三处独立可做，优先对话侧）：
1. `AttachmentOrchestrator.process`：附件级并行——每个附件一个
   `CompletableFuture.supplyAsync(() -> 下载+处理, 附件池)`，`allOf` 汇总后按原序组装；
2. `AttachmentImageProcessor.processImages`：图片 caption 并行发起（每图一个 future），
   **按位置预分配序号**（「图片N」编号由下标决定，不依赖完成顺序），join 后按序收集，
   序号语义与现状完全一致；
3. `EtlPipeline.buildChunkSpecs`：图片分区先收集（过滤+字节去重后），并行执行
   upload+caption，再按文档原顺序组装 specs（chunkIndex 顺序不变）。

线程池：新建独立附件处理池（core 2~4，有界队列，AbortPolicy——与 ETL/检索/记忆池隔离，
符合「各业务独立线程池」）；ETL 图片并行**不得复用 etlPool**（etlPool 2~4 线程已被
processDocument 主任务占用，子任务排队会自锁死）。VLM/embedding 并发度设上限
（信号量或池大小 = 2~4），避免触发 DashScope QPS 限流。

预期收益：多附件消息处理时长从 Σ 降为约 max：3 图 caption 3~6s → 1~2s；2 文档 + 3 图混合
消息下载与 caption/文档处理互相重叠。ETL 图片密集文档 chunking 阶段同比例缩短。

风险与一致性影响：中低。① 单项失败隔离语义必须保持（现状 try-catch 跳过单项——并行后
每 future 独立 catch，等价）；② Caffeine `get(key, fn)` 原子单飞特性保留（并行下同 hash
并发首跑仍只执行一次）；③ VLM 并发可能触碰 DashScope 限流，需小并发起步观察；
④ 结果组装顺序（caption 序号、chunkIndex、documents 键序）必须按输入位置回填，不能按完成顺序。

## P2-3. RetrieveNode 三段并行编排受 2 线程池限制，最重的知识检索最后才获得线程

- 档位：高置信可落地
- 位置：`backend/src/main/java/com/commerce/rag/bot/graph/RetrieveNode.java:199-219`（池定义 :123-138、
  `application.yml:152` `retrieval.retrieve-node-parallelism: 2`）

现状代码：

```java
// RetrieveNode.apply（08-22 报告 2-3 已实施的并行编排）
CompletableFuture<String> userDocFuture = CompletableFuture.supplyAsync(
        () -> buildUserDocumentText(attachmentContext, originalQuery), retrieveExecutor); // 任务① 占线程A

float[] preVector = embedSafely(queries.get(0).queryText());  // ← 主线程同步 embed，数百 ms

CompletableFuture<Void> episodicFuture =
        CompletableFuture.runAsync(() -> recallEpisodic(config, plan, preVector), retrieveExecutor); // 任务② 占线程B
CompletableFuture<List<KnowledgeChunk>> chunksFuture = CompletableFuture.supplyAsync(
        () -> searchKnowledgeTool.searchKnowledge(queries, preVector).chunks(), retrieveExecutor);    // 任务③ 排队！

episodicFuture.join();
List<KnowledgeChunk> chunks = chunksFuture.join();
```

问题分析：retrieveExecutor 是固定 2 线程（`newFixedThreadPool(2)`），而编排提交了 3 个任务，
且提交顺序固定：①userDoc 最先占线程 → 主线程同步 embed（数百 ms）→ ②episodic 占最后一个
线程 → ③**知识检索（三段中最重：多查询 Milvus hybridSearch + rerank）进队列等待**，
直到 ①或② 之一完成才能开始。无附件时 ①立即返回 null（`hasAny()==false`）释放线程，
③马上获得线程，并行完好；**有文档附件时**①内部还有一次 `embed(originalQuery)`（数百 ms）
加逐附件局部检索，③被推迟——实际延迟退化为 `embed + max(①,②) + ③`，而设计目标是
`max(三段)`。恰好附件场景是 IO 最重的场景，2-3 优化的收益在该场景被线程池瓶颈吃掉大半。

优化方案（两选一或叠加）：
1. **把预嵌入也移进池内**（消除主线程同步等待 + 任务链化）：
   ```java
   CompletableFuture<float[]> preVecFuture =
           CompletableFuture.supplyAsync(() -> embedSafely(queries.get(0).queryText()), retrieveExecutor);
   CompletableFuture<Void> episodicFuture =
           preVecFuture.thenAcceptAsync(v -> recallEpisodic(config, plan, v), retrieveExecutor);
   CompletableFuture<List<KnowledgeChunk>> chunksFuture =
           preVecFuture.thenApplyAsync(v -> searchKnowledgeTool.searchKnowledge(queries, v).chunks(), retrieveExecutor);
   ```
2. **parallelism 2→3**（`application.yml` 一行，或默认值改 3）：三任务各有线程，
   提交顺序不再影响开始时间。

方案 1 在 2 线程下仍有排队但等待被 embed 与 userDoc 的重叠吸收；方案 2 最简单直接。
metadata 写入仍保持在 join 后主线程（与现状一致，无可见性问题）。

预期收益：有附件的 knowledge_question 对话，检索节点延迟从「三段部分串行」回到
「约等于最慢一段」——附件 embed（数百 ms）不再推迟知识检索的开始时间。
无附件场景无变化（现状已最优）。

风险与一致性影响：低。并行结构、降级语义（embedSafely 返回 null 时 recall 跳过、检索自嵌
兜底）完全不变；仅线程调度顺序变化。3 线程 daemon 池的内存开销可忽略。

## P2-4. 分片落库仍逐条 insert（M-1 批量化只做了 UPDATE 半边）

- 档位：高置信可落地（收益中小）；历史延续项——08-16 M-1 建议含「先批量插入全部分片」，
  当前只实施了 next_chunk_id 的批量 UPDATE，INSERT 侧未动
- 位置：`backend/src/main/java/com/commerce/rag/etl/EtlPipeline.java:268-298`（循环体 `chunkMapper.insert(chunk)`:290）

现状代码：

```java
// chunkDocument：M-1 注释声称「落库（M-1：next_chunk_id 回填收集后单条批量 UPDATE）」，
// 但 insert 本身仍逐条：
for (ChunkSpec spec : specs) {
    DocumentChunk chunk = new DocumentChunk();
    // ... 组装 17 个字段 ...
    chunk.setPrevChunkId(prevChunkId);
    chunkMapper.insert(chunk);                        // ← N 个分片 = N 次单条 INSERT 往返
    if (prevChunkId != null) {
        linkPairs.add(new ChunkLinkPair(prevChunkId, chunk.getId()));  // 依赖 insert 回填的雪花 ID
    }
    prevChunkId = chunk.getId();
}
if (!linkPairs.isEmpty()) {
    chunkMapper.batchUpdateNextChunkIds(linkPairs);   // ✓ UPDATE 已批量化
}
```

问题分析：百 chunk 文档 chunking 阶段产生 100 次单条 INSERT 网络往返（+1 次去重查询 +
1 次批量链回填 UPDATE）。逐条的原因是 prevChunkId 需要上一行的雪花 ID——但 MP 的
ASSIGN_ID 在 insert 时填充实体，链回填本来就是落库后独立的批量 UPDATE，说明「先批量插入、
插入后再组装链」在结构上完全可行，insert 逐条并非必要。

优化方案：`DocumentChunkMapper.xml` 新增 `batchInsert`（foreach multi-values INSERT）；
ID 供给两选一：① 注入 MyBatis-Plus 的 `IdentifierGenerator` bean 循环 `setId`（与 MP
insert 内部同一机制，**非**宪法禁止的 `IdWorker` 静态工具），insert 语句显式携带 id 列；
② PG `INSERT ... RETURNING id` 由 MyBatis 接收回填。插入完成后组装 linkPairs，
复用既有 `batchUpdateNextChunkIds`。事务包裹（与现状一致，process 无 @Transactional，
建议批量化后 chunk 落库段补事务保证原子——软删旧 chunk 与插入新 chunk 已是两次写）。

预期收益：百 chunk 文档 PG 往返从约 102 次降为 3 次（软删 1 + 批插 1 + 链回填 1），
chunking 阶段缩短约百 ms（内网 RTT 量级）；非交互路径，属确定性小收益。

风险与一致性影响：低。multi-values 单语句天然原子（无需额外事务即可整批成功/失败）；
需覆盖单测（既有 chunkDocument 测试 mock 的是 insert 调用次数，需改为校验 batchInsert 参数）。
注意 batchInsert 的 foreach 分批（如 500/批）防超长 SQL。

## P2-5. chunk 更新/批量标注在 HTTP 请求线程同步执行 embedding + Milvus 重建

- 档位：存疑待判断；历史延续项——08-16 M-4 建议「reEmbedAndUpsert 提交 etlPool 异步执行」，
  当年仅实施了 syncDocToMilvus 的批量化，异步化未实施
- 位置：`backend/src/main/java/com/commerce/rag/service/impl/DocumentChunkServiceImpl.java:157`
  （updateContent 调 reEmbedAndUpsert）、`:393-395`（batchUpdate 循环逐文档 syncDocToMilvus）；
  底层 `etl/EtlPipeline.java:600-624`（reEmbedAndUpsert：embed HTTP + PG update + Milvus
  delete/insert）、`:759-785`（syncDocToMilvus：**全列查询含 dense_vector BYTEA** + delete + insert）

现状代码：

```java
// updateContent（PUT /api/v1/admin/chunks/{id}/content）—— HTTP 请求线程内：
etlPipeline.reEmbedAndUpsert(id);   // 1 次 embedding HTTP（秒级）+ 1 次 PG update + 2 次 Milvus 调用

// batchUpdate（PUT /api/v1/admin/chunks/batch）—— 请求线程内循环：
for (Long docId : docIds) {
    etlPipeline.syncDocToMilvus(docId);   // 每文档：chunk 全列查询（含向量 BYTEA）+ Milvus delete + insert
}
```

问题分析：两个 B 端接口在 Tomcat 请求线程内同步执行远程调用链。updateContent 单次
（1 embed + 2 Milvus）秒级尚可接受；batchUpdate 若勾选的 chunk 跨多个大文档（每文档
数百 chunk），每文档拉取全部分片含 1024 维 float 向量字节（每 chunk 约 4KB 向量，
500 chunk ≈ 2MB/文档）+ 2 次 Milvus 往返，跨 10 文档即数十 MB 传输 + 20 次 Milvus 调用，
接口超时风险高（HTTP 默认 30s~60s 网关超时）。

不确定点（为何存疑）：① B 端使用频率与单批文档规模未知——若教师标注操作低频且
单批 1~2 个中等文档，现状耗时可控；② 异步化改变「更新返回后立即可检索」的语义
（转异步后检索到旧 course_id 有窗口期），需产品拍板；③ 异步失败对 B 端的反馈通道
（现状失败上抛可重试，异步后需轮询或通知）。08-16 用户对 M-4 的批量化部分已裁决实施
（「调用次数=文档数而非分片数」），异步化当时未一并采纳，推测有意保留同步语义。

优化方案（若拍板异步化）：`syncDocToMilvus`/`reEmbedAndUpsert` 提交 etlPool，
batchUpdate 立即返回并携带「已受理文档数」；文档可复用 parse_status 相邻字段或新增
sync_status 标记同步中/完成/失败供前端轮询。保守替代（不异步）：至少把 batchUpdate 的
逐文档循环改为分批并行（2 并发）+ syncDocToMilvus 的全列查询按需投影（向量列必须取，
但 metadata_json 等可省）。

预期收益：跨多文档批量标注接口从秒~分钟级阻塞（超时风险）降为立即返回；
请求线程释放。

风险与一致性影响：异步化引入「PG 已改、Milvus 未同步」窗口——course_id 过滤检索在该窗口
用旧值（与现状 P0-1 修复前的症状同源但窗口更短）；失败需补偿机制。需用户/产品拍板后再动。

## P2-6. ETL 链路外部调用无显式超时，Milvus gRPC 无 deadline

- 档位：存疑待判断；历史延续项——08-16 M-7 建议含「各阶段提交 Future + get(timeout）」，
  当年仅实施了 AbortPolicy 快速失败（队列满场景），「任务挂起」场景无保护
- 位置：`backend/src/main/resources/application.yml`（spring.ai.openai/dashscope 无任何
  timeout 配置项）、`config/MilvusConfig.java:24-33`（MilvusClientV2 builder 无超时参数）、
  `etl/EtlPipeline.java` 全文（无 Future/get(timeout)）；对照已保护路径：
  `worker/ChatRequestWorker.java:490`（blockLast 5min）、`bot/tool/SearchKnowledgeTool.java:190`
  （allOf.get 10s）、application.yml `memory.extraction.timeout-ms: 10000`

问题分析：ETL 管道（etlPool 仅 2~4 线程）内的 embedding 批量调用、VLM caption、
Milvus insert/delete 均无应用侧超时。任一外部依赖挂起（网络分区、服务端 hang）即永久
占用一个 etlPool 线程，文档永久滞留 PARSING/CHUNKING/EMBEDDING 中间态——与 chat_run 不同，
**document 表没有 stale 状态巡检**（M-8 只给 run 加了 60s 巡检），卡死文档无法自愈、
无法重跑（process 入口的 CAS 抢占只接受 PENDING/FAILED）。对话链路的 QU/主模型调用同样
无显式超时，但受 blockLast(5min) 兜底（代价是用户等 5 分钟才收到错误，期间 runPool
线程被占）。检索超时已完备（10s）。

不确定点：① Spring AI 1.1.2 的 RestClient 默认超时行为未在本仓库可验证（若 Boot 3.5
默认工厂带有限 read timeout，则对话链路风险低于描述；ETL 链路同受益但上限更低）；
② SAA DashScope 原生 SDK（embedding/rerank 通道）自带默认超时与否未知；
③ Milvus Java SDK v2 的 gRPC 默认 deadline 行为未知。三项都需实测（挂起模拟）确认
现状风险敞口，故列存疑。

优化方案：
1. RestClient 层统一超时（一次配置全链路受益）：`RestClientCustomizer`/`ClientHttpRequestFactorySettings`
   设 connect 5s / read 120s（LLM 生成可长，但必须有界）；
2. Milvus `ConnectConfig` 设 connectTimeout/超时参数（SDK 支持的范围内核实）；
3. ETL 兜底巡检：复用 M-8 的 ScheduledExecutor 模式，每 5~10min 扫
   `document.parse_status IN (中间态) AND updated_at < now()-阈值` 置 FAILED
   （幂等，CAS 抢占天然支持重跑收敛）。

预期收益：故障场景爆炸半径从「永久占线程 + 文档永久卡死 + 后续上传因池满被拒」
收窄为「可感知的 FAILED 状态 + 可重试」。

风险与一致性影响：超时值需权衡长文档（VLM caption 慢）误杀——read timeout 给足余量
（120s+），巡检阈值给足（30min+）。客户端工厂定制影响全部 AI 通道，需回归 QU/检索/生成链路。

## P2-7. Tika 图片字节全量堆驻留至 chunk 阶段结束

- 档位：存疑待判断
- 位置：`backend/src/main/java/com/commerce/rag/etl/TikaImageExtractor.java:47`（parseEmbedded
  `readAllBytes` 全量收）、`etl/EtlPipeline.java:112,210`（parsedContentCache 持有
  ParsedContent——含全部图片字节——直至 chunkDocument 完成）

现状代码：

```java
// TikaImageExtractor.parseEmbedded：每张内嵌图片字节全量驻留
byte[] bytes = stream.readAllBytes();
images.putIfAbsent(resourceName, new ParsedContent.CapturedImage(bytes, ...));  // LinkedHashMap 累积
```

问题分析：文档上限 100MB（`etl.max-file-size-mb: 100`）。图片密集型 PDF 的图片字节全部
驻留堆内（解析阶段 → XhtmlDocumentParser → parsedContentCache → chunkDocument 消费完才释放）；
etlPool 4 线程并发处理 4 个图片密集文档时峰值堆压力可达数百 MB（字节 × 4 任务 + XHTML
文本副本 + caption 输入再持有）。缓存清理路径完备（finally + 两处 remove，08-15 P3-3 已修），
问题仅在**峰值驻留**而非泄漏。

不确定点：实际知识库文档的图片密集度未知——以文字为主的 PDF（每文档 <10 张小图）
驻留可忽略；扫描版/图册型 PDF 才构成压力。无实测内存数据前无法定级，列存疑。

优化方案（若实测有压力）：① 过滤前置——小于 `image-min-size-kb` 的图片字节不入
CapturedImage（当前过滤发生在 buildImageChunk，字节已经驻留过了，把 ImageFilter 判定
提前到 parseEmbedded 可裁掉大头小图标）；② 超大单图（>5MB）直接跳过 caption 分支或
落临时文件。方案 ① 改动极小且无语义损失（被过滤图片本来就不产出 chunk）。

预期收益：图片密集文档 ETL 峰值堆占用下降（小图标通常是数量大头）；GC 压力降低。

风险与一致性影响：过滤前置需保证与 `ImageFilter.isSmallIcon/isDecorative` 判定完全同参
（同 `etl.image-min-size-kb`），避免两处阈值漂移；`getImages()` 的消费方
（XhtmlDocumentParser 按 img src 定位）对缺失图片需容忍（现状 buildImageChunk 返回 null
已有容忍路径，需确认 parser 侧不强依赖 images 全集）。
