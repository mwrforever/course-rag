## 一、结论摘要

S1 经历记忆链路整体工程质量高：线程池隔离（偏好/经历/检索各自独立）、防抖 latest-wins、
召回侧 PG 批量 in 取数（已规避 N+1）、V12 索引覆盖查询路径、best-effort 降级语义均合规。
本次发现的优化点集中在**提取落库事务**与**检索节点串行链路**两处：

| # | 优先级 | 位置 | 问题 | 类型 |
|---|--------|------|------|------|
| 1 | **[高]** | EpisodicMemoryServiceImpl.applyExtraction | 决策阶段循环内逐条查 (user_id,type)，N+1 次 PG 往返 | N+1/批量 |
| 2 | **[高]** | EpisodicMemoryServiceImpl.execute | embedding HTTP + Milvus upsert 在 @Transactional 事务内串行执行，持锁时间被远程 IO 放大 | 事务/IO |
| 3 | **[中]** | RetrieveNode.apply | episodic 召回 → 知识检索 → 附件局部检索三段独立 IO 完全串行，白占对话关键路径 | 异步/并行 |
| 4 | **[中]** | PromptLoader.loadSections | 唯一无缓存的模板加载方法，QU 节点每轮对话读盘 + YAML 解析 | 缓存 |
| 5 | [模糊] | RetrieveNode + SearchKnowledgeTool | 首条重写查询同文本两次 embedding 远程调用 | 重复 IO |
| 6 | [模糊] | MemoryExtractionPipeline | 防抖 Map 为实例内状态，多实例部署时去重失效（非性能，顺带提示） | 部署形态 |

Redis/Lua 原子化专项：**本批提交无新增高并发 Redis 竞态项**（详见第五节），无需 Lua 改造。

## 二、优化项明细

### 2-1【高】applyExtraction 决策阶段 N+1 查询 —— 循环内逐条查 (user_id, type)

**位置**：`backend/src/main/java/com/commerce/rag/service/impl/EpisodicMemoryServiceImpl.java:87-99`

**问题**：LLM 单批可产出多条记忆（prompt 未限制 `episodic_memories` 条数，对话含多个事实点时常见 2~5 条），
现实现对每条记忆单独发起一次 PG 查询取该 (user_id, type) 的既有行——N 条记忆 = N 次数据库往返。
虽有 `idx_episodic_user_type` 索引支撑、单次查询很快，但网络往返次数随条数线性增长，属典型 N+1。

```java
// EpisodicMemoryServiceImpl.java:87-99（现状：每条记忆一次查询）
for (EpisodicMemoryExtraction memory : result.memories()) {
    List<UserEpisodicMemory> rows = this.lambdaQuery()
            .select(
                    UserEpisodicMemory::getId,
                    UserEpisodicMemory::getType,
                    UserEpisodicMemory::getContent,
                    UserEpisodicMemory::getSummary,
                    UserEpisodicMemory::getValidity,
                    UserEpisodicMemory::getVersion)
            .eq(UserEpisodicMemory::getUserId, userId)
            .eq(UserEpisodicMemory::getType, memory.type())   // ← 循环变量作条件，逐条往返
            .list();
    actions.add(decisionEngine.decide(memory, rows));
}
```

**优化方案**：type 为 4 值白名单（`EpisodicTypes.ALL_TYPES`），先对本批 distinct type 一次
`in (types)` 查询取回全部相关行，内存按 type 分组后逐条决策——N 次往返收敛为 1 次：

```java
// 建议形态（伪代码）
List<String> types = result.memories().stream()
        .map(EpisodicMemoryExtraction::type).distinct().toList();
Map<String, List<UserEpisodicMemory>> rowsByType = this.lambdaQuery()
        .select(/* 同现有列 */)
        .eq(UserEpisodicMemory::getUserId, userId)
        .in(UserEpisodicMemory::getType, types)               // 一次批量取回
        .list().stream()
        .collect(Collectors.groupingBy(UserEpisodicMemory::getType));
for (EpisodicMemoryExtraction memory : result.memories()) {
    actions.add(decisionEngine.decide(memory,
            rowsByType.getOrDefault(memory.type(), List.of())));
}
```

**语义与风险**：`EpisodicDecisionEngine.decide` 只消费"该 type 的行列表"，分组后输入等价，
决策结果不变；同一事务内无并发写入者（提取流水线同用户 30s 防抖串行化），无脏读引入。
建议顺手在 select 列中补 `UserEpisodicMemory::getUserId`（供 2-2 的索引同步复用旧行，见下）。

### 2-2【高】事务内远程 IO —— embedding HTTP 与 Milvus upsert 拉长 PG 事务持锁时间

**位置**：`EpisodicMemoryServiceImpl.java:76-156`（`applyExtraction` @Transactional → `execute` → `syncIndexBestEffort`）

**问题**：`applyExtraction` 标注 `@Transactional`，事务体内的 `execute` 对每个生效动作调用
`syncIndexBestEffort(() -> buildUpsert(...))`，而 `buildUpsert` 内部先调
`embeddingModel.embed(text)`（DashScope qwen3.7-text-embedding 远程 HTTP，单次数百 ms），
再 `milvusClientV2.upsert`（远程 gRPC）。即：**每个生效动作 1~2 次远程 HTTP + 1~2 次远程 gRPC
全部串行发生在未提交的 PG 事务内**。一批 N 条动作时事务持锁/占连接时长 ≈ N × (embed 延迟 + Milvus 延迟)，
可达秒级；提取高峰（多用户 run 同时完成、经历+偏好双流水线并发）时线性放大 DB 连接池占用，
拖累同库的对话主链路（chat_run 状态写、消息持久化）。

```java
// EpisodicMemoryServiceImpl.java:117-156（节选，现状：索引同步在事务内）
private int execute(Long userId, Long sourceSessionId, EpisodicAction action) {
    switch (action.type()) {
        case CREATE -> {
            UserEpisodicMemory row = toWriteRow(userId, sourceSessionId, action, "active");
            save(row);
            syncIndexBestEffort(() -> buildUpsert(row, "active"));   // ← embed(HTTP) + upsert(gRPC) 在事务内
        }
        case UPDATE, MERGE -> {
            ...
            syncIndexBestEffort(() -> buildUpsertById(...));          // ← 事务内还额外反查一次 PG（见下）
            syncIndexBestEffort(() -> buildUpsert(row, "active"));
        }
        ...
    }
}

// EpisodicMemoryServiceImpl.java:333-343（buildUpsert 内的远程调用）
public UpsertReq buildUpsert(UserEpisodicMemory row, String validity) {
    String text = (row.getSummary() == null ? "" : row.getSummary()) + "\n"
            + (row.getContent() == null ? "" : row.getContent());
    float[] vector = embeddingModel.embed(text);                      // ← DashScope HTTP
    ...
}
```

**优化方案**（三层，可独立实施）：

1. **索引同步挪到事务提交后**：事务内只收集待同步的行（新建行对象 + 状态流转的旧行 id/type/validity），
   `TransactionSynchronizationManager.registerSynchronization` 的 `afterCommit` 中统一执行
   embed + upsert。事务体收敛为纯 SQL（毫秒级），best-effort 失败语义不变（提交后失败仅记日志）。
2. **合并 upsert 请求**：`buildMemoryUpsert` 现每次仅携带一行（`data(List.of(row))`）；一批动作的
   多个新行/旧行流转可合并为一次多行 upsert（Milvus UpsertReq.data 天然支持 List），远程调用次数
   从 O(动作数) 降为 O(1)~O(2)。
3. **消除 buildUpsertById 的事务内反查**：UPDATE/MERGE 分支为组装旧行 embedding 反查一次 PG
   （`EpisodicMemoryServiceImpl.java:353-360`）。决策阶段其实已取到该行（只是 select 列缺
   user_id/summary/content 中部分列），在 2-1 的批量查询中补齐 `user_id` 列并让 `EpisodicAction`
   携带旧行引用，即可完全省掉这次反查。

**风险与注意**：afterCommit 中抛出的异常不会回滚事务（本就是 best-effort，可接受）；
需确认 `TransactionSynchronizationManager.isSynchronizationActive()`（applyExtraction 可能被
无事务上下文直测调用），非活动时降级为直接同步执行，保持单测可直测性。

### 2-3【中】RetrieveNode 三段独立 IO 串行 —— episodic 召回可移出对话关键路径

**位置**：`backend/src/main/java/com/commerce/rag/bot/graph/RetrieveNode.java:165-203`

**问题**：`apply` 返回 `CompletableFuture` 但方法体同步串行执行三段相互独立的远程 IO：

1. `recallEpisodic(...)`（第 170 行）：embed(HTTP) → Milvus search → PG 批量取数，三段串联；
2. `searchKnowledgeTool.searchKnowledge(queries)`（第 173-174 行）：知识混合检索（内部已有 4 线程并行）；
3. `mergeUserDocument(...)` → `buildUserDocumentText` → `embeddingModel.embed(originalQuery)`（第 311 行，
   有文档附件时再来一次 embed HTTP + 内存余弦局部检索）。

三段结果互不依赖（episodic_context 与 document_context 是 metadata 上两个独立键，
附件局部检索也不消费前两者输出），当前却串成一串——episodic 召回整段延迟（embed 数百 ms + Milvus + PG）
与附件 embed 延迟全部叠加进每轮 knowledge_question 对话的检索节点，直接推高首 token 延迟。
检索节点阻塞期间占用 runPool（8 线程）worker 线程，高并发对话时放大吞吐损失。

```java
// RetrieveNode.java:165-177（现状：串行三段）
recallEpisodic(config, plan, queries.get(0).queryText());   // ① embed + Milvus + PG，同步阻塞

// 4. 检索（并行 + RRF 融合 + SHA256 去重 + Rerank 在 SearchKnowledgeTool 内完成）
List<KnowledgeChunk> chunks =
        searchKnowledgeTool.searchKnowledge(queries).chunks();   // ② 整块等①完成才开始
AttachmentContext attachmentContext = readAttachmentContext(config);
...
String document = contextBuilderService.buildDocument(...);      // ③ 附件分支再 embed(originalQuery)
```

**优化方案**：按工程宪法「并行场景用 CompletableFuture（多查询检索、附件批处理）」，
将 ① 与 ②（及有附件时的 ③ embed）并行：

```java
// 建议形态（伪代码）：episodic 召回与知识检索并行，join 后各自写 metadata
CompletableFuture<Void> episodicFuture = CompletableFuture.runAsync(
        () -> recallEpisodic(config, plan, queries.get(0).queryText()), executor);
CompletableFuture<List<KnowledgeChunk>> chunksFuture = CompletableFuture.supplyAsync(
        () -> searchKnowledgeTool.searchKnowledge(queries).chunks(), executor);
episodicFuture.join();                      // recallEpisodic 内部已全异常降级，不会抛出
List<KnowledgeChunk> chunks = chunksFuture.join();
```

检索节点延迟从「三段之和」降为「约等于最慢一段」。episodic 召回自身已是全链路 try-catch
降级（`RetrieveNode.recallEpisodic` + `EpisodicMemoryServiceImpl.recall` 双层兜底），并行化后
失败隔离语义不变。

**执行器选择**：不宜复用 `SearchKnowledgeTool` 私有 searchExecutor（会与知识检索互相争抢 4 线程，
形成自阻塞风险——若 5 条查询占满线程池，episodic 任务排队等知识检索反而更慢）；
建议 RetrieveNode 注入独立小线程池（2 线程足够，或复用项目既有检索类线程池配置）。
metadata 写入放在 join 后由主线程执行，避免两个并行任务写同一 Map 的可见性问题。

### 2-4【中】PromptLoader.loadSections 无缓存 —— QU 节点每轮对话读盘 + YAML 解析

**位置**：`backend/src/main/java/com/commerce/rag/bot/graph/PromptLoader.java:96-107`

**问题**：同一个类里 `load()`/`loadRaw()` 均有 `ConcurrentHashMap` 缓存，唯独 `loadSections()`
每次调用都执行 `new ClassPathResource(...).getInputStream()` 磁盘读取 + snakeyaml 解析。
调用方共 4 处，其中 **QueryUnderstandingService 是每轮对话 QU 节点的必经路径**：

| 调用方 | 频率 |
|--------|------|
| `bot/rewrite/QueryUnderstandingService.java:88`（query-understanding.yml） | **每轮对话一次** |
| `etl/ImageCaptionService.java:44`（caption.yml） | 每张图片附件 |
| `service/PreferenceExtractionService.java:65` | 30s 防抖级（低频） |
| `service/EpisodicExtractionService.java:62` | 30s 防抖级（低频） |

```java
// PromptLoader.java:39-41（load 有缓存） vs 96-107（loadSections 每次读盘解析）
public String load(String fileName) {
    return cache.computeIfAbsent(fileName, this::doLoad);          // ✓ 缓存
}
...
public Map<String, String> loadSections(String fileName) {
    try (InputStream is = new ClassPathResource("prompts/" + fileName).getInputStream()) {
        Map<String, Object> data = yaml.load(is);                  // ✗ 每次磁盘 IO + YAML 解析
        ...
        log.info("已加载提示词模板(sections): {} ({} 段)", fileName, result.size());
        return result;
    } catch (Exception e) { ... }
}
```

**优化方案**：与 `load`/`loadRaw` 同款缓存即可（模板为 classpath 静态资源，启动后不变，
无一致性维护成本）：

```java
private final Map<String, Map<String, String>> sectionsCache = new ConcurrentHashMap<>();

public Map<String, String> loadSections(String fileName) {
    return sectionsCache.computeIfAbsent(fileName, fn -> {
        Map<String, String> loaded = doLoadSections(fn);
        return Collections.unmodifiableMap(loaded);   // 防调用方修改污染共享缓存
    });
}
```

**注意**：必须返回不可变包装（或每次浅拷贝）——缓存的 Map 会被多个调用方共享，
现在返回的独立 LinkedHashMap 无此问题，加缓存后需补这层防护。另 `loadSections` 每次
打 info 日志，缓存后自然消除每轮对话一条模板加载日志的噪音。

## 三、模糊项（附源码佐证，供判断）

### 3-1【模糊】首条重写查询同文本两次 embedding 远程调用

RetrieveNode 把 `queries.get(0).queryText()`（首条重写查询）交给 `recallEpisodic`，
其内部 `embeddingModel.embed(queryText)` 发起一次 DashScope HTTP；随后知识检索的
`SearchKnowledgeTool.searchSingle` 对**同一文本**再 embed 一次。同文本两次远程调用，
各占数百 ms 延迟与一份 API 费用：

```java
// EpisodicMemoryServiceImpl.recall（第一次，episodic 召回用）
float[] vector = embeddingModel.embed(queryText);          // queryText = queries.get(0).queryText()

// SearchKnowledgeTool.searchSingle（第二次，知识检索用）
float[] denseVector = embeddingModel.embed(query.queryText());   // query[0] 同一文本
```

**可选方案 a（接口传向量，零重复但侵入接口）**：RetrieveNode 层预先 embed 一次，
`recall` 与检索链改为接收向量。改动面：`IEpisodicMemoryService.recall` 签名 + SearchKnowledgeTool
入口，侵入中等。
**可选方案 b（EmbeddingModel 短 TTL 缓存，全局收益但影响面广）**：文本 sha256 → 向量的
Caffeine 缓存（5~10min TTL，数千条容量）。同文本必然同向量（embedding 为确定性函数），
一致性风险仅在模型版本更换时刻（发版重启即失效，天然规避）。收益顺延到 ETL/附件/caption
全链路，但会改变所有 embed 调用行为，建议单独评估。

> 标注为模糊的原因：方案 a 侵入接口、方案 b 影响全局，两者都与 2-3 的并行化有交互
> （并行化后两次调用已不叠加在关键路径上，仅剩 API 费用与 DashScope 侧延迟），是否值得改取决于
> 对 embedding 费用与配额的敏感度，需人工拍板。

### 3-2【模糊】MemoryExtractionPipeline 防抖状态为实例内 Map —— 多实例部署时去重失效

`pending/pendingEpisodic/futures/futuresEpisodic` 均为 JVM 内 ConcurrentHashMap（latest-wins 合并、
重复调度取消）。单实例部署下语义正确（同用户 30s 窗口仅执行一次提取）；若未来水平扩容多实例，
同用户的 run 可能落不同实例，各自独立提取一次——`applyExtraction` 事务 + 状态机能兜住数据一致性
（最坏多一次 UPDATE/MERGE 版本流转），不会脏写，但 LLM 提取调用翻倍。

> 非本批引入的性能问题，当前单实例架构下无需处理；若引入多实例，届时可将防抖标记放 Redis
> （SET NX EX 30s）实现跨实例去重，属部署形态决策，提请知悉。

## 五、Redis / Lua 原子化专项结论

本批提交未引入新的 Redis 竞态项：

- 提取流水线的防抖/合并为 JVM 内 `ConcurrentHashMap` + `ScheduledFuture.cancel`，
  单实例下无跨线程竞态（latest-wins 即目标语义），无需 Lua；
- `ChatRequestWorker` 消费采用「读到即 ACK + chat_run 状态兜底」（P3-2 已裁决），
  无 pending 争抢；`cancelFlags`/巡检均为单实例内状态；
