## 二、优化项明细

### P1-1. ETL 分片/向量化阶段逐 chunk 串行 IO（[存量]，7042265/62e0e5c 扩展了该阶段）

**位置**：`backend/src/main/java/com/commerce/rag/etl/EtlPipeline.java`

**问题**：一个文档 N 个分片，两个阶段共约 5N 次外部调用：

`chunkDocument()`（EtlPipeline.java:198-233）循环内：
- 每 chunk 1 次 `chunkMapper.insert(chunk)`（单条 INSERT）
- 每 chunk 1 次 `updateChunkNextId(prevChunkId, chunk.getId())`（单条 UPDATE）

`embedAndIndex()`（EtlPipeline.java:272-296）循环内：
- 每 chunk 1 次 `embeddingModel.embed(chunk.getContent())`（Embedding API 网络调用，**最慢**）
- 每 chunk 1 次 `updateChunkVector(...)`（单条 UPDATE BYTEA）
- 每 chunk 1 次 `insertToMilvus(chunk, vector, ...)`（单条 Milvus insert，insertToMilvus 内 `data(List.of(row))` 只插 1 行，EtlPipeline.java:464-467）

以一份 200 分片的文档计：PG 400 次单条写 + 200 次 Embedding 网络调用 + 200 次 Milvus 写 ≈ 800 次串行外部调用，ETL 全链路耗时被放大 1~2 个数量级。

**建议**（按收益排序）：
1. **PG 批量插入**：document_chunk 批量 insert 走 mapper XML（`<foreach>`，宪法允许的复杂场景），一次插入全部 chunk；插入后再按 chunk_index 顺序批量 `UPDATE next_chunk_id`（`<foreach>` 批量 update，或按 `doc_id + chunk_index` 排序关联一次 UPDATE 语句）。
2. **Embedding 批量**：Spring AI `EmbeddingModel` 提供批量 `embed(List<String>)` 接口，一次请求处理多文本；注意按配置分批（如 16~32 条/批）控制单请求体量与超时。
3. **Milvus 批量插入**：`InsertReq.builder().data(rows)` 支持 List<JsonObject> 多行一次插入（当前 `List.of(row)` 只传 1 行），每批 20~50 行。
4. **实体复用**：`process()` 全流程 4 次 `selectById(docId)`（process:98 / parseDocument:136 / chunkDocument:174 / embedAndIndex:254），同一线程同一 docId 可一次查询后参数传递，省 3 次主键查询。

**影响**：ETL 吞吐提升数倍，embedding API 调用次数减少为 N/批大小。

### P1-2. 知识库删除循环逐对象 MinIO 删除（[24h 引入]，91605c6）

**位置**：`backend/src/main/java/com/commerce/rag/service/KnowledgeBaseService.java:165-171`

```java
List<Document> docs = documentMapper.selectList(
        new LambdaQueryWrapper<Document>().eq(Document::getKbId, id).select(Document::getSourcePath));
for (Document d : docs) {
    if (d.getSourcePath() != null) {
        minioStorageService.deleteFile(d.getSourcePath());
    }
}
```

**问题**：一个知识库 N 个文档 = N 次 MinIO removeObject 网络往返，串行执行；文档多时删除接口秒级超时。

**建议**：MinIO SDK 提供 `removeObjects(RemoveObjectsArgs)` 批量删除（一次请求删多个对象，服务端批量执行）。在 `MinioStorageService` 增加批量删除方法（对象列表分批，如 100 个/批），`KnowledgeBaseService.delete` 改调批量方法。注意保留当前"失败上抛阻断"语义：批量删除按批失败即抛，PG 软删不执行，可重试收敛（removeObject 幂等）。

### P2-1. 分片批量端点权限校验 2N 次主键查询（[24h 引入]，580434c 契约对齐）

**位置**：`backend/src/main/java/com/commerce/rag/service/DocumentChunkService.java`

`batchUpdate()`（:274-294）与 `batchCorrected()`（:303-318）对每个 id 循环调用 `checkOwnership(id, ...)`，
而 `checkOwnership()`（:365-380）内部 2 次 selectById：

```java
private void checkOwnership(Long chunkId, Long userId, boolean isAdmin) {
    ...
    DocumentChunk chunk = chunkMapper.selectById(chunkId);   // 第 1 次
    Document doc = documentMapper.selectById(chunk.getDocId()); // 第 2 次
    ...
}
```

批量 N 个分片 = 2N 次单条主键查询。

**建议**：批量校验改为 2 次查询：`chunkMapper.selectBatchIds(ids)` 一次取全部分片 → 收集去重后的 docId 列表 → `documentMapper.selectBatchIds(docIds)` 一次取文档 → 内存逐一校验 created_by。同时单个分片接口（D1 findById:70-80）也存在"先 selectById 再 checkOwnership 内再 selectById"的同行重复查询，可一并消除（checkOwnership 改为接收已查实体或返回实体）。

### P2-2. 课程数据读多写少无缓存（[存量]，24h 内 c8bede0 扩展了工具聚合查询）

**位置**：`backend/src/main/java/com/commerce/rag/bot/tool/CourseApiTool.java` / `service/CourseQueryService.java`

**问题**：
- `queryCourseDetail()`（CourseApiTool.java:80-112）每调用 3 次查询（课程 + 内容 + 下一期排期）；
- 这是 LLM agent 工具，一轮对话内 LLM 可能多次调用（先 listCourses 再 queryCourseDetail/queryEnrollment），每轮对话重复查库；
- 课程数据是典型的读多写少（创建/更新为管理端低频操作），完全适合缓存。

**建议**：`CourseQueryService` 的查询结果加 Caffeine 本地缓存（TTL 5~10 分钟，容量按课程数设上限）：
- 缓存失效时机（一致性铁律：先写 DB 后失效缓存）：`CourseService.createCourse/updateCourse/deleteCourse`、`updateContent/batchUpdateContents`、课程排期变更处，按 courseId 精确失效。
- 列表查询（searchCourses）可缓存或不做（涉及分页+关键词，命中率低，建议只缓存单课程聚合：findCourseById / findContentsByCourseId / findNextSchedule）。
- 多实例部署时本地缓存有短暂不一致窗口，TTL 内可接受（课程数据不敏感）；如需要强一致再改 Redis。

### P2-3. Dashboard 统计端点每次实时计算（[24h 引入]，9c03905）

**位置**：`backend/src/main/java/com/commerce/rag/service/DashboardService.java`

**问题**：
- `dashboardStats()`（:46-54）每次 2 条 count（document 全表 + document_chunk 按 correction_status）；
- `feedbackStats()`（:61-75）每次 3 条 count（chat_run + user_feedback 赞 + user_feedback 总，其中赞/总两条 count 可合并为一条 `SUM(CASE WHEN is_liked THEN 1 ELSE 0 END)`）；
- 管理端刷新 dashboard 即触发，属"常用统计 + 分钟级新鲜度"场景。

**建议**：Caffeine 本地缓存（TTL 60s，或按数据变更失效）：
- 失效时机：上传文档/ETL 完成（DocumentService.upload/reparse、EtlPipeline 终态）、反馈提交（UserFeedbackService.create/delete）时失效对应统计键。
- 收益：dashboard 打开从 3~5 条 SQL 降为 0 条（缓存命中）。

### P3-1. 反馈意图统计 1+2N 次查询（[存量]）

**位置**：`backend/src/main/java/com/commerce/rag/service/UserFeedbackService.java:110-139`

```java
// 查询所有不重复的 intent_type
... .select(UserFeedback::getIntentType).groupBy(UserFeedback::getIntentType);
for (UserFeedback type : types) {   // 每类 2 次 count
    feedbackMapper.selectCount(... eq(intentType).eq(isLiked, true));
    feedbackMapper.selectCount(... eq(intentType).eq(isLiked, false));
}
```

**问题**：按意图分组后逐类 2 次 count。意图类型数量有界（knowledge_question/chat/unknown/null），当前 N≤4，开销尚可，但一条 SQL 可完全替代，且随业务扩展意图类型会线性放大。

**建议**：mapper XML 一条 `GROUP BY intent_type` + `SUM(CASE WHEN is_liked THEN 1 ELSE 0 END) / SUM(CASE WHEN is_liked = false THEN 1 ELSE 0 END)`（或 `count(*) FILTER (WHERE ...)`）一次返回全部统计。

### P3-2. 教师分片过滤"全量 id + IN"（[存量]）

**位置**：`backend/src/main/java/com/commerce/rag/service/DocumentChunkService.java:104-115`（findPage）与 :343-354（findPending）

```java
LambdaQueryWrapper<Document> docWrapper = new LambdaQueryWrapper<Document>()
        .eq(Document::getCreatedBy, userId).select(Document::getId);
List<Long> docIds = documentMapper.selectList(docWrapper).stream()...;
wrapper.in(DocumentChunk::getDocId, docIds);
```

**问题**：教师拥有大量文档（数千）时：① 应用层取全量 doc id 列表（内存占用）；② `IN (...)` 数千个 id 的 SQL 超长、执行计划退化。

**建议**：改 mapper XML 子查询形态：`WHERE doc_id IN (SELECT id FROM document WHERE created_by = ? AND deleted = 0)`（document.created_by 已有索引，见 V6 迁移 idx_document_created_by），DB 侧完成过滤，应用层零搬运。教师文档量在百级以下时可不改（当前可接受）。

### P3-3. ETL 解析文本缓存异常路径残留（[存量]，24h 内 7042265 强化了异常处理）

**位置**：`backend/src/main/java/com/commerce/rag/etl/EtlPipeline.java:78-79, 182-185, 238-239`

```java
private final ConcurrentHashMap<Long, String> parsedTextCache = new ConcurrentHashMap<>();
// parseDocument 成功 put(docId, text)；chunkDocument 末尾 remove(docId)
```

**问题**：`parsedTextCache.remove(docId)` 只在 chunkDocument 成功路径执行；若 parse 成功 → chunk/embed 阶段抛异常（process() 的 catch 置 FAILED 退出），缓存永不清理，docId 为全局唯一递增键，长期运行（含反复 reparse 失败）内存持续增长。

**建议**：`process()` 的 catch/finally 中统一 `parsedTextCache.remove(docId)`（与 removeRing 同模式）；或改用 `Cache`（Caffeine，TTL 30min）天然兜底。属资源管理，非 IO 性能。

## 三、已核查无问题（避免重复优化）

- **聊天消息落库**：`ChatMessageService.batchInsert` 用 JdbcTemplate.batchUpdate 批量插入（ChatMessageService.java:59-72），已是最优形态。
- **RT 一次性旋转/设备互踢/禁用用户**：全部走单条 Lua 脚本原子化（mark_rt_used.lua / kick_and_login.lua / disable_user.lua），无应用层读-改-写竞态，符合"高流量并发项 Lua 原子"要求。
- **SSE 流式链路**：MemoryStreamBridge 为纯内存 ring buffer（256 容量），`replayAndSubscribe` 锁内回放+注册、锁外 send（IO 不持锁），`close()` 遍历 complete——无 DB/文件 IO 热点；XADD 失败回滚与 removeRing 兜底完整（f4cea95）。
- **上传/下载流关闭**：上传 try-with-resources（AdminDocumentController.java:83-87）；ETL 下载 try-with-resources（EtlPipeline.java:146）；下载响应由 Spring `ResourceHttpMessageConverter` 复制后关闭流。
- **黑名单/互踢查询**：`isBlacklisted` 走 Redis O(1)（DeviceKickService.java:161-185），PG 仅为降级路径；key 全部带 TTL，无永久缓存。
- **索引完备性**：V6 迁移 55 个索引覆盖 document_chunk(doc_id+chunk_index / course_id / correction_status+kb_id)、chat_message(run_id+seq / session_id+seq)、user_feedback(intent+liked) 等全部查询路径；`chat_run` 缺 created_at 单列索引但表量级小（每会话一行），count 全表扫可接受。
- **课程列表接口**：AdminCourseController.list 使用 `toDTO(c, false)`，不含关联查询，无 N+1（仅 detail 端点单课程 3 次查询，可接受）。

## 四、建议实施顺序

1. **P1-1 ETL 批量化**（收益最大）：文档分片批量 insert + next_chunk_id 批量 update + embedding 分批 + Milvus 批量 insert + 实体复用。
2. **P1-2 知识库删除 MinIO 批量**：新增 `removeObjects` 批量方法，删除接口改调用。
3. **P2 三项**：批量端点权限校验批量化 → 课程 Caffeine 缓存（含失效钩子）→ Dashboard 统计缓存（含失效钩子）。
4. **P3 三项**：findStats 单条 SQL、教师过滤子查询、parsedTextCache 清理。
