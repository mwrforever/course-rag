## 二、优化项明细

### H-1（高，[新]）SSE 事件推送同步阻塞在生成线程，慢客户端拖停整条生成链路

**位置**：`worker/ChatRequestWorker.java:296-304`（doOnNext 内同步 push）+ `stream/MemoryStreamBridge.java:170-173`（push 内逐订阅者 `emitter.send`）+ `ChatRequestWorker.java:345`（`blockLast` 单线程驱动全图）。

**问题**：整个 Reactor 图由 runPool 一个线程通过 `blockLast(5min)` 驱动，每条 SSE 事件在 `doOnNext` 内对每个订阅者同步执行 `SseEmitter.send`（阻塞网络 IO）。慢客户端（TCP 缓冲满/断线未感知）会使 `send` 阻塞 → 卡住 `doOnNext` → 整条 LLM 生成链路被迫暂停；runPool 仅 CPU×2≈8 线程，多个慢客户端即可占满全部生成线程，叠加队列 100 + CallerRuns 后全管道停摆。

```java
// ChatRequestWorker.java:296-304（简化）
.doOnNext(chunk -> {
    ...
    List<SseEvent> events = transformer.transform(chunk, runState);
    events.forEach(e -> bridge.push(runIdStr, e));   // 同步 send
})
...
.blockLast(Duration.ofMinutes(5));                   // 同线程驱动
```

```java
// MemoryStreamBridge.java:170-172
for (SseEmitter emitter : subscribers) {
    sendEvent(emitter, event);   // 每个订阅者同步阻塞 IO
}
```

**建议**：事件投递与生成解耦——每 run 一个**有界发送队列 + 独立投递线程**（或对 `emitter.send` 加超时并摘除坏订阅者），慢客户端只丢自己（或进降级），不拖累生成线程。注意保持事件顺序（单投递线程天然有序）。改造成本中等，收益在并发连接数上升后显著。

### H-2（高，[新]）设备互踢"预读 TTL"竞态——并发登录时旧 RT 漏进黑名单，互踢失效

**位置**：`auth/DeviceKickService.java:121-132`（Lua 执行前 Java 预读 `GET auth:cur:{userId}:{deviceType}` 决定 `oldAtTtl/oldRtTtl`）+ `resources/lua/kick_and_login.lua:31-37`（Lua 内重新 GET，黑名单 SETEX 条件依赖 ARGV[3]/ARGV[4] > 0）。

**问题**：TTL 决策（Java 预读）与踢出决策（Lua 内 GET）分离，存在 TOCTOU 竞态：

```
T0：并发登录 A、B 均 Java 预读 GET → 都读到 null（oldAtTtl=oldRtTtl=0）
T1：A 的 Lua 先执行，写入 A，old=null → 无踢出
T2：B 的 Lua 执行，GET 到 old=A → kicked=true，但 ARGV[3]/ARGV[4]=0 → A 的 jti 不写黑名单
```

后果：A 的会话指针被覆盖但 RT 未进黑名单 → A 可正常 refresh 续命，**并发登录下双会话并存，互踢安全边界被绕过**。另外注释声称"查询旧 AT 的剩余 TTL"，实际恒传全量 TTL，注释与实现不符。

```java
// DeviceKickService.java:121-132 —— 非原子预读
String old = redisTemplate.opsForValue().get(curKey);
if (old != null && !old.isEmpty()) {
    String[] parts = old.split("\\|");
    if (parts.length >= 1 && !parts[0].isEmpty()) oldAtTtl = authProperties.accessTokenExpiry();
    if (parts.length >= 2 && !parts[1].isEmpty()) oldRtTtl = authProperties.refreshTokenExpiry();
}
```

```lua
-- kick_and_login.lua —— 黑名单条件依赖预读值
if old_jti_at ~= '' and tonumber(ARGV[3]) > 0 then
    redis.call('SETEX', 'auth:bl:' .. old_jti_at, tonumber(ARGV[3]), ...)
```

**建议**：删除 Java 预读（读-改-写全部原子化于 Lua，正合"高流量并发用 Lua 原子解决"）——固定传 `accessTokenExpiry/refreshTokenExpiry` 全量 TTL（黑名单多留无害，过期自动清理），旧设备是否存在由 Lua 内 GET 决定；顺带修正方法注释。修复成本极低（删 10 行 + 参数固定），建议优先。

### H-3（高，[延续]）ETL 向量化阶段逐 chunk 串行 embedding + 逐条 PG/Milvus IO

**位置**：`etl/EtlPipeline.java:299-323`（embedAndIndex 循环）+ `insertToMilvus:570-593`（`data(List.of(row))` 单行插入）。

**问题**：每个 chunk 串行执行「embedding API 远程调用 + `updateChunkVector` 单条 UPDATE + Milvus 单行 insert」——一次文档数百分片即数百次 embedding 调用 + 数百次 PG 写 + 数百次 Milvus 写，分钟级耗时。08-15 报告 P1-1 已报，本窗口未修复。

```java
// EtlPipeline.java:299-315
for (DocumentChunk chunk : chunks) {
    float[] vector = embeddingModel.embed(chunk.getContent());   // 串行单条远程调用
    ...
    updateChunkVector(chunk.getId(), denseVector, String.valueOf(chunk.getId())); // 单条 UPDATE
    insertToMilvus(chunk, vector, doc.getTitle());               // 单行 InsertReq
}
```

```java
// EtlPipeline.java:587-590
InsertReq insertReq = InsertReq.builder()
        .collectionName(COLLECTION_NAME)
        .data(List.of(row))     // 仅 1 行，Milvus v2 支持多行
        .build();
```

**建议**：① embedding 走 Spring AI `EmbeddingModel.embed(List<String>)` 批量接口（每批 16~32 条，**待确认**当前实现类 DashScope 对批量接口的支持）；② Milvus `InsertReq.data(rows)` 一次多行（每批 20~50 行）；③ PG 向量回写改为批量 UPDATE（`CASE WHEN id ... END` 或按 doc_id 一次更新）。收益：ETL 吞吐提升数倍、embedding 调用次数降为 N/批大小。

### M-1（中，[延续]）ETL 分片落库逐条 insert + 逐条 update（2N 条 SQL）

**位置**：`etl/EtlPipeline.java:223-260`（chunkAndSave 循环）。

**问题**：每 chunk 先 `chunkMapper.insert(chunk)` 再 `updateChunkNextId(prevChunkId, chunk.getId())` 回填 next_chunk_id，N 个分片 = 2N 次单条 SQL（08-15 P1-1 已报，未修）。

**建议**：两阶段批量化——先 `saveBatch` 批量插入全部分片（MP 雪花 ID 自动生成），插入完成后收集 (id, prevChunkId) 映射，对"有前驱的 chunk"执行一条批量 UPDATE 回填（`<foreach>` 或 `CASE WHEN id THEN ...`）。

### M-3（中，[新]）断线重连回放在 stateLock 锁内逐条 sendEvent，慢客户端持锁阻塞 Worker push

**位置**：`stream/MemoryStreamBridge.java:229-244`（replayAndSubscribe 在 `synchronized (stateLock)` 内逐条 sendEvent，ring 最多 256 条）。

**问题**：回放期间的网络 IO 持锁执行，而 Worker 的 `push` 写入 ring 需同一把锁（`Ring.push:157-168`）——慢客户端回放数秒则该 run 实时推送全部排队，生成停摆。注：锁内发送是 P1-1 的**有意设计**（保证回放事件先于注册后推送的实时事件交付，避免乱序），修复需保持该顺序语义。

**建议**：锁内仅收集回放事件快照（浅拷贝引用列表）并完成订阅注册，锁外再逐条发送（顺序仍保持：发送完成前 Worker 的新事件虽已入 buffer，但因注册先于发送，新事件可能先到——需在快照发送完之前不推新事件，可将"注册"延迟到快照发送完成后，中间用已注册标记拦截）；或限定单次回放最大条数分批发送、对 send 加超时摘除坏订阅者。

### M-4（中，[新]）分片更新/标注在 HTTP 请求线程同步执行 embedding + Milvus 重建

**位置**：`service/impl/DocumentChunkServiceImpl.java:137-155`（updateContent 调 `etlPipeline.reEmbedAndUpsert`）、`:290-317`（batchUpdate 逐文档 `syncDocToMilvus`）；`etl/EtlPipeline.java:352-376/509-537`。

**问题**：`PUT /api/v1/admin/chunks/{id}/content` 在请求线程内同步调 embedding API（秒级）+ Milvus delete/insert；批量标注对每个涉及文档逐 chunk 执行「delete + insert」两条 Milvus 调用，大文档（数百 chunk）上千次 Milvus 往返阻塞请求线程，接口超时风险高。

**建议**：`reEmbedAndUpsert` 提交 `etlPool` 异步执行（前端轮询状态或复用文档状态机）；`syncDocToMilvus` 改为批量 delete（`deleteFromMilvusByChunkIds` 已存在）+ 单次多行 InsertReq。

### M-5（中，[新]）J2 课程资料全列查询（含 dense_vector BYTEA）+ 无分页

**位置**：`service/impl/DocumentChunkServiceImpl.java:259-264`（findByCourseId，调用方 StudentController.java:96-104 courseMaterials）。

**问题**：`selectList` 不带 `.select(...)` 取回 document_chunk 全列（含 content 长文本、metadata_json、**dense_vector BYTEA 向量**），而 `ChunkVO` 只用 7 列，其余全部丢弃；且课程专属资料无分页（J3 通用资料库有分页），课程分片多时一次返回数百条全列数据。

### M-6（中，[新]）黑名单清理先全表查再逐条 UPDATE（N+1）

**位置**：`service/impl/SysLoginRecordServiceImpl.java:231-243`（cleanupExpiredBlacklist）。

**问题**：先 `selectList` 拉回全部过期黑名单记录，再循环逐条 UPDATE；而同一类上方 `cleanupExpired:151-160` 已是单条 UPDATE 的正确范式。


### M-7（中，[新]）ETL 全链路无超时 + 队列满 CallerRuns 内联阻塞上传请求线程

**位置**：`etl/EtlPipeline.java`（processDocument/parseDocument/chunkDocument/embedAndIndex 全程无超时）+ `config/EtlConfig.java:30-44`（core=2, max=4, queue=20, CallerRunsPolicy）+ `service/impl/DocumentServiceImpl.java:135/316`（`etlPool.execute` 上传/reparse 入口）。

**问题**：Tika 解析、embedding、Milvus 调用均无超时配置，etlPool 仅 4 线程，任一任务挂死即永久占用一线程；队列 20 满后 CallerRunsPolicy 让**上传/reparse 的 HTTP 请求线程内联执行整个 ETL**，分钟级任务直接阻塞上传接口。

**建议**：各阶段提交 `Future` + `get(timeout)` 加超时与中断；或 watchdog 扫描超时任务 `cancel(true)`；上传入口队列满时改为快速失败（拒绝 + 状态回写 PENDING/FAILED）而非 CallerRuns 内联。

### M-8（中，[新]）Worker 单消费者 + 队列满 CallerRuns 内联 + 读到即 ACK

**位置**：`worker/ChatRequestWorker.java:161-205`（consumeLoop）+ `config/WorkerConfig.java:46-56`。

**问题**：消费只有一个 `chat-consumer` 线程；runPool 满（8 线程全被最长 5 分钟 run 占用 + 队列 100 满）时 CallerRunsPolicy 让消费者线程**内联执行** run——消费循环停摆，Redis Stream 所有新对话滞留。先 ACK 后执行（P3-2 用户裁决）使进程崩溃时消息直接丢失（无 pending 可回收），且 chat_run 滞留 ACTIVE 被 `uniq_active_run_per_session` 唯一索引锁死（该会话后续对话恒 409）。

**建议**：① 多消费者线程（2~4 个）分担内联；② 队列满时回写 run=ERROR 并 ACK（快速失败）而非内联执行；③ 增加"长时间 ACTIVE 的 run 巡检"定时任务（扫 chat_run 超时 ACTIVE → 置 FAILED/ERROR 解锁）；④ ACK 时机改"执行完成后 ACK"需与用户裁决相悖，仅提示。
