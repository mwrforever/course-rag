## P1-1. 通用资料库 `course_id='DEFAULT'` 查询被 partial 索引显式排除，每次 J3 分页全表扫

- 档位：高置信可落地
- 位置：`backend/src/main/resources/db/migration/V6__full_schema_v5.sql:88`；调用查询 `backend/src/main/java/com/commerce/rag/service/impl/DocumentChunkServiceImpl.java:347-359`（findByCourseIdDefaultAsVO，入口 StudentController.java:100-110 J3 端点）

现状代码：

```sql
-- V6__full_schema_v5.sql:88 —— partial 索引显式排除 DEFAULT 行
CREATE INDEX idx_document_chunk_course ON document_chunk(course_id)
    WHERE course_id != 'DEFAULT' AND deleted = 0;
```

```java
// DocumentChunkServiceImpl.java:347-352 —— J3 查询条件恰是被排除的值
LambdaQueryWrapper<DocumentChunk> wrapper = Wrappers.<DocumentChunk>lambdaQuery()
        .eq(DocumentChunk::getCourseId, "DEFAULT")     // ← 索引条件是 != 'DEFAULT'，此查询必然无法命中
        .orderByAsc(DocumentChunk::getChunkIndex);
IPage<DocumentChunk> entityPage = chunkMapper.selectPage(pageObj, wrapper);
```

问题分析：document_chunk 是全库最大表（单文档数百分片，dense_vector BYTEA 每行约 6KB）。partial 索引 `idx_document_chunk_course` 的条件是 `course_id != 'DEFAULT'`，**DEFAULT 行根本不在索引内**——`course_id = 'DEFAULT'` 的 J3 分页查询（含 MP 分页自动生成的 count 查询，每页请求 2 条 SQL）没有任何可用索引，只能顺序全表扫描 + 按 chunk_index 排序。表增长后 C 端学生浏览通用资料库的每次翻页成本线性恶化。顺带：J2（具体课程）虽可命中该单列 partial 索引，但 `ORDER BY chunk_index` 仍需额外排序。

优化方案：新增 Flyway 迁移（V13）一条非 partial 复合索引，同时覆盖 J2/J3 的过滤与排序：

```sql
CREATE INDEX idx_document_chunk_course_index
    ON document_chunk(course_id, chunk_index) WHERE deleted = 0;
```

预期收益：J3 每次分页请求（count + page 两条 SQL）从全表扫 + 排序降为索引范围扫描；J2 消除排序阶段。纯 DDL，零代码改动，旧索引可保留（或评估后删除 idx_document_chunk_course 避免写放大）。
一致性影响：无缓存交互；索引由 PG 自动维护，无失效问题。

## P1-2. evictCourse 漏失效 `byTitle:*` 缓存键——课程增删改名后课程名映射最长 5 分钟脏读

- 档位：高置信可落地
- 位置：`backend/src/main/java/com/commerce/rag/service/impl/CourseQueryServiceImpl.java:184-190`（evictCourse），对照 `:165-173`（findByTitle 缓存键 `byTitle:{title}`）

现状代码：

```java
// CourseQueryServiceImpl.java:165-173 —— findByTitle 结果缓存 5 分钟
public List<CourseInfo> findByTitle(String title) {
    String key = "byTitle:" + title;
    List<CourseInfo> cached = (List<CourseInfo>) courseQueryCache.get(key, k -> {
        return courseInfoMapper.selectList(Wrappers.<CourseInfo>lambdaQuery()
                .select(CourseInfo::getId, CourseInfo::getTitle, CourseInfo::getStatus)
                .eq(CourseInfo::getTitle, title));
    });
    return cached;
}

// CourseQueryServiceImpl.java:184-190 —— 失效只清 search:*，不含 byTitle:*
public void evictCourse(Long courseId) {
    String id = String.valueOf(courseId);
    courseQueryCache.invalidate("course:" + id);
    courseQueryCache.invalidate("contents:" + id);
    courseQueryCache.invalidate("schedule:" + id);
    courseQueryCache.asMap().keySet().removeIf(k -> k.startsWith("search:"));   // ← byTitle:* 漏了
}
```

问题分析：`findByTitle` 是每轮 knowledge_question 对话 QU 节点课程名→course_id 映射（retrieval/CourseNameMapper.java:54）的底座。`createCourse / updateCourse / deleteCourse / updateContent / batchUpdateContents / 排期写` 全部只调 `evictCourse`，而它不清理 `byTitle:*` 键，违反「先写 DB 后失效缓存」铁律的完整性要求：
- 删除课程后 5 分钟内，`byTitle:{title}` 仍返回已删课程 → QU 过滤收窄到已删课程 → 检索空结果；
- 改名后旧名仍映射到该课程、新名查不到（新名若曾被缓存为空列表，Caffeine 不缓存 null 返回但空列表会缓存）；
- 新建同名课程后，同名映射漏掉新课程。

优化方案：与 `search:*` 同款前缀清理，一行改动：

```java
courseQueryCache.asMap().keySet()
        .removeIf(k -> k.startsWith("search:") || k.startsWith("byTitle:"));
```

预期收益：课程增删改名后 QU 课程过滤立即正确（消最长 5 分钟脏窗口）。改动成本一行。
一致性影响（失效策略）：写方先写 DB 后调 evictCourse 的既有顺序不变；本项即失效策略本身的补全——byTitle 键值域小（课程名数量级），整前缀清理成本可忽略。

## P1-4. ETL 分片落库仍逐条 insert——M-1 只落地了链路回填批量化 [延续 08-16 M-1]

- 档位：高置信可落地
- 位置：`backend/src/main/java/com/commerce/rag/etl/EtlPipeline.java:268-298`（chunkDocument 落库循环，insert 在 :290）；顺带 `:131/:173/:229/:504` process 链 4 次 selectById [延续 08-15 P1-1 第 4 点]

现状代码：

```java
// EtlPipeline.java:268-298 —— next_chunk_id 已收集批量回填，但 insert 本身仍逐条
for (ChunkSpec spec : specs) {
    DocumentChunk chunk = new DocumentChunk();
    ... // 15+ 个字段组装
    chunkMapper.insert(chunk);                        // ← N 个分片 = N 次单条 INSERT
    if (prevChunkId != null) {
        linkPairs.add(new ChunkLinkPair(prevChunkId, chunk.getId()));
    }
    prevChunkId = chunk.getId();
}
if (!linkPairs.isEmpty()) {
    chunkMapper.batchUpdateNextChunkIds(linkPairs);   // ← 回填已批量化（M-1 半量）
}
```

问题分析：08-16 M-1 建议两阶段批量化（saveBatch 批量插入 + 批量回填），当前只实施了回填半段，插入仍是 N 次单条 SQL 往返（一份 200 分片文档 = 200 次 insert + 1 次批量回填）。MP 的 ASSIGN_ID 雪花在 insert 前填充到实体，saveBatch 后每个实体已有 ID，链表构建逻辑不变。另：process → parseDocument → chunkDocument → embedAndIndex 各自 selectById 同一 docId（4 次主键查询），可入口查一次后参数传递。

优化方案：EtlPipeline 注入 `IDocumentChunkService`（或 mapper XML `<foreach>` 批量 insert），组装完 List 后一次 `saveBatch`（须在事务内，宪法要求）；插入后照旧构建 linkPairs 走既有批量回填。process 主流程实体复用：process 查到的 doc 以参数传递给三阶段（或 parsedContentCache 同款 docId→实体传递）。
预期收益：每文档 N 次 insert 往返 → ceil(N/1000) 次批处理（200 分片省 ~199 次往返），ETL 落库阶段耗时明显收缩；省 3 次冗余主键查询。
一致性影响：saveBatch 事务语义与现状逐条非事务 insert 相比是收紧（原子性增强）；dashboard 统计失效时机（CHUNKED 状态写入后）不变。

## P1-5. 反馈创建 selectOne + insert/update 两往返，可 ON CONFLICT 单条 SQL [延续 08-16 L-6]

- 档位：高置信可落地
- 位置：`backend/src/main/java/com/commerce/rag/service/impl/UserFeedbackServiceImpl.java:65-104`（create）

现状代码：

```java
// UserFeedbackServiceImpl.java:67-94 —— 先查后写两往返
UserFeedback existing = feedbackMapper.selectOne(
        Wrappers.<UserFeedback>lambdaQuery()
                .eq(UserFeedback::getUserId, userId)
                .eq(UserFeedback::getMessageId, messageId));
if (existing != null) {
    feedbackMapper.update(null, updateWrapper);       // 往返 2a
    ...
} else {
    feedbackMapper.insert(feedback);                  // 往返 2b
}
```

问题分析：赞/踩是 C 端学生对每条 AI 回复都可触发的高频交互。表已有 `uniq_feedback_message(user_id, message_id)` 唯一索引（V6:325），当前实现：① 常态 2 次数据库往返；② 并发双击（同用户同消息两个请求同时通过 selectOne 判空）第二个 insert 撞唯一索引抛 DataIntegrityViolation → 全局处理器映射 500，既丢正确性又浪费一次往返（08-15 报告附注已提示）。

优化方案：mapper XML 单条 upsert（宪法允许的复杂 SQL 形态）：

```sql
INSERT INTO user_feedback (user_id, session_id, message_id, is_liked, intent_type, ...)
VALUES (...)
ON CONFLICT (user_id, message_id) WHERE deleted = 0
DO UPDATE SET is_liked = EXCLUDED.is_liked, intent_type = EXCLUDED.intent_type
RETURNING id, is_liked, intent_type
```

service 侧一次调用拿回落库后行，照旧失效 dashboardStatsCache（先写 DB 后失效顺序保持）。
预期收益：高频路径 2 次往返 → 1 次；并发双击语义从 500 变为幂等更新。
一致性影响：dashboardStatsCache 失效时机与现状一致（SQL 执行成功后 invalidateAll）。
