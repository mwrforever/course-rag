# 中置信风险与待观察问题清单（机制确认，触发条件苛刻或危害有限）

- **风险类别**：混合（审计一致性 / TOCTOU / fail-open / 竞态 / 阻塞 / 死配置）
- **严重度**：P2~P3（建议与 P0/P1 一并规划，不阻塞首轮修复）
- **变更范围**：未提交工作区全部新增代码

## 1. 设备互踢 Redis 路径不更新 PG 审计（A10）—— 审计一致性

- 证据：`DeviceKickService.java:117-135` Lua 执行成功后仅 `parseKickResult(result)` 返回，**未**将旧 login_record 置 REVOKED、未回填 PG 黑名单；对比 PG 降级路径（:313-331）有完整 REVOKED + 黑名单写入。设计文档 §5.2 要求"PG 异步审计回填"。
- 影响：旧设备 login_record 永久保持 ACTIVE；`disableUser` 的 `findActiveLoginRecords`（:415-420）重复捞到已踢设备；审计统计"活跃会话数"失真。无安全危害，数据脏。

## 2. RT 一次性旋转非原子（A11）—— TOCTOU 竞态

- 证据：`AuthController.java:178-191` `isRefreshTokenUsed` 检查与 `DeviceKickService.java:196-209` `markRefreshTokenUsed` 为两次独立 Redis 调用，中间无原子性（无 Lua/单命令）。
- 影响：同一 RT 并发两个 refresh 请求均通过检查 → 签发两对新 Token，"复用即全量作废"不触发。需并发窗口，危害中。

## 3. 黑名单校验 fail-open（A12）—— 安全降级方向

- 证据：`DeviceKickService.java:160-168` `isBlacklisted` 在 Redis 与 PG **同时**查询失败时 `return false`（放行）。
- 影响：双故障时被吊销/被踢 token 全部放行。属降级权衡，但方向与安全预期相反（fail-open vs fail-closed）。建议至少记 error 日志并限流兜底。

## 4. reclaimPending 对排队消息 XCLAIM 后重复执行（B8）—— 双执行竞态

- 证据：`ChatRequestWorker.java:203-205` runPool.submit 后消息即入 PEL；`:265-284` reclaimPending 对 idle >30min 的 pending 消息 XCLAIM 并重新 submit；`processRequest` 全程无"runId 已处理/已 ACK"幂等检查，`updateStatus` 无条件覆盖。
- 影响：runPool 积压 >30min（8 线程 × 每 run 最长 5min，持续超负荷）→ 同一条消息执行两次 → 同一 runId 双跑：SSE 事件重复推送、chat_message 重复落库（叠加 B3）、cancelFlags 被 finally 互相清除。

## 5. WarningHook 检测状态取消/异常路径不清理（B9）—— 内存残留 + 跨 run 污染

- 证据：`WarningHook.java:510-519` `cleanupThreadState` 仅在 afterModel 的 `!assistantMsg.hasToolCalls()` 分支（:217-219）调用；取消是 Worker 在图外抛 `CancelledException` 中断订阅（`ChatRequestWorker.java:367-375`），该轮 afterModel 不保证执行。`detectionStates`（key=threadId=sessionId）条目保留旧 token 累计/工具计数。
- 影响：会话被取消/出错后，同一 session 下次 run 继承上次的累计计数 → 可能误触发"Token 预算硬停/循环硬停"；长期不自然结束的会话使 map 无界增长。

## 6. Ring.push 同步阻塞写多个 SseEmitter（B11）—— 慢客户端拖垮 runPool

- 证据：`MemoryStreamBridge.java:171-174` `Ring.push` 在 Worker 线程内对每个订阅者同步 `emitter.send()`（SseEmitter 底层为阻塞 socket write），失败（IOException）才移除；运行中 run 可被多个客户端同时订阅（chat + 多个 reconnect）。
- 影响：任一客户端 TCP 窗口填满不消费 → 该 run 的所有推送阻塞 worker 线程 → runPool 被占满、队列积压（放大 B8）。Spring 侧 write 为阻塞写，属已知模式风险；无缓冲/背压策略。

## 7. ETL 无类型白名单 + maxFileSizeMb 死配置（C15）

- 证据：`AdminDocumentController.java:213-219` `extractFileExtension` 对任意扩展名放行（前端文档限定 PDF/PPTX/DOCX/MD/TXT）；`EtlProperties.java:28` 定义 `maxFileSizeMb`（application.yml:135=100）全仓库无引用（grep 证实），实际仅靠 servlet multipart 100MB 兜底。
- 影响：可上传 .exe/.zip 等任意类型，ETL 解析失败堆积 FAILED 文档与 MinIO 对象（叠加 C14 流泄漏）。

## 8. SOURCES 事件可能永远不发（观察）

- 证据：`SseEventTransformer.java:227-252` `buildSourcesEvent` 假设 `ToolResponseMessage.responseData()` 是 `KnowledgeSearchResult` 的 JSON；若 SAA 对 record 返回值走 `toString()`（`KnowledgeSearchResult[chunks=[...]]` 非 JSON），`readTree` 失败返回 null → SOURCES 静默缺失。需运行时实证，无法定论。

## 9. 死代码（低危，按 AGENTS.md 应清理）

- `ChatRequestWorker.java:92,354,412` `ThreadLocal<RunSnapshot> runSnapshot` 只 set/remove 从不读取（注释声称 Hook 可读，但 Hook 是独立 bean 无法访问）；
- `SseEvent.java:27-29` `toSseText()` 未被引用；
- `ChatRunService.findActiveRun/cancelRun`（:96-115）无调用方；
- `AuthConfig.java:28` 排除 `/api/v1/public/**` 但全仓库无该前缀端点。
