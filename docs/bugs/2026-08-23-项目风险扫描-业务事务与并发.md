## B2-1. runPool 队列满快速失败不推终态事件且不清理 ring——客户端永久"生成中" + Ring/投递线程泄漏

- **严重度**：高
- **置信度**：高
- **位置**：`backend/src/main/java/com/commerce/rag/worker/ChatRequestWorker.java:266-283`（拒绝分支）；关联 `stream/ChatStreamEntry.java:150-155`（入口先建 ring/订阅）、`stream/MemoryStreamBridge.java:63-64/127-132`（ring 生命周期）
- **引入提交**：`0ffe128`（fix: 24h 审查 bug/性能清单修复……M-1~8，M-8 引入"快速失败"）
- **问题描述与证据**：
  ```java
  // ChatRequestWorker.consumeLoop（0ffe128）
  ackMessage(msg.getId().getValue());          // 消息已 ACK（P3-2 裁决）
  try {
      runPool.submit(() -> processRequest(msg));
  } catch (RejectedExecutionException e) {
      Object runIdObj = msg.getValue().get("runId");
      ...
      chatRunService.updateStatus(rejectedRunId, "ERROR");   // 只回写 DB
      log.error("runPool 队列已满，run 快速失败（消息已 ACK）: runId={}", runIdObj);
  }
  ```
  拒绝分支仅回写 run=ERROR：① 不向 ring 推送 ERROR 终态事件；② 不调用 `bridge.removeRing(runIdStr)`（`removeRing` 只在 `processRequest` 的 finally 与入口 XADD 失败路径调用，而 `processRequest` 此刻根本没有机会执行）。
- **影响**：
  1. **客户端永久"生成中"**：`ChatStreamEntry.chat()` 在 XADD 前已 `createRing + subscribe`，客户端 emitter 靠心跳撑住 30 分钟，无任何终态事件。**重连也无法恢复**：`reconnect` 走 `bridge.replayAndSubscribe` 时 ring 存在且未 close（`outbox` 空、必返回 true），不会进入查 PG 补终态的降级分支——重连后依旧无事件，直到 30 分钟 emitter 超时，再重连再挂。
  2. **资源泄漏**：每个被拒 run 泄漏一个 Ring（含 `LinkedBlockingQueue` + 一个阻塞在 `outbox.take()` 的 `bridge-delivery-{runId}` daemon 线程），`rings` ConcurrentHashMap 条目永不移除。持续过载时随拒绝数线性增长。
  3. runPool 为 8 线程 + 100 队列（`application.yml:289-296`），单 run 最长 5 分钟（blockLast 超时），持续 ≥2 req/s 的对话流量即可在分钟级填满队列，触发并非极端。
- **建议修复方向**：拒绝分支补 `bridge.push(ERROR 事件)` + `bridge.removeRing(runId)`（与 `handleError` 对齐终态语义）；顺带可在 ring 层加"run 终态后 ring 延迟关闭"兜底。

## B2-2. reparse 无在执行守卫，重置 PENDING 绕过 ETL CAS 抢占——同文档双管道并发

- **严重度**：高
- **置信度**：高
- **位置**：`backend/src/main/java/com/commerce/rag/service/impl/DocumentServiceImpl.java:292-323`（reparse）；`backend/src/main/java/com/commerce/rag/etl/EtlPipeline.java:128-161`（process 抢占）
- **引入提交**：抢占守卫 `7042265`（fix: P2-1 ETL 状态守卫——注释自称"从根上消除并发双跑"）；reparse 现行结构 `64096a6` 及更早
- **问题描述与证据**：
  ```java
  // DocumentServiceImpl.reparse：对当前 parseStatus 无任何检查，无条件重置
  documentMapper.update(null, Wrappers.<Document>lambdaUpdate()
          .eq(Document::getId, id)
          .set(Document::getParseStatus, "PENDING") ...);
  submitEtlOrFail(id);

  // EtlPipeline.process：CAS 只拦"两个 process() 并发"，拦不住已被重置回 PENDING 的在执行文档
  int claimed = documentMapper.update(null, Wrappers.<Document>lambdaUpdate()
          .eq(Document::getId, docId)
          .in(Document::getParseStatus, "PENDING", "FAILED")   // ← reparse 刚把执行中文档改回 PENDING
          .set(Document::getParseStatus, "PARSING") ...);
  ```
  大 PDF 的 ETL 全程（解析→分片→逐批 embedding）可达分钟级；期间用户在管理端点击"重新解析"（`AdminDocumentController.java:141-145` 直通 service，无状态校验），即可让第二个 ETL 抢占成功，与第一个并发执行。
- **影响**（多路交错均可实证）：
  1. **重复/交错分片**：两个 `chunkDocument` 的 delete-then-insert（`EtlPipeline.java:257-298`）互相软删对方已插入的行、又各自继续插入；sha256 去重是"查库跳过"（`idx_document_chunk_sha256` 为**非唯一**部分索引，V6:95），竞态下双方查库时对方未插入 → 同内容双份 active chunk 落库（检索结果重复、chunk_count 错乱）。
  2. **parsedContentCache 互踩**：`parsedContentCache` 是 per-doc 单槽 ConcurrentHashMap（`EtlPipeline.java:112`）；先完成一方的 `finally { parsedContentCache.remove(docId) }`（:159）会让未到 chunkDocument 的另一方抛 `IllegalStateException("解析结果为空或未找到")`（:239）→ 整管道标 FAILED。
  3. **终态互相覆盖**：`updateDocStatus` 全部无条件写入；晚收尾的失败方把 INDEXED 覆盖成 FAILED（或反之），文档状态与实际索引不一致。Milvus 侧 `embedAndIndex` 的 delete-then-insert 同样双跑交错。
- **建议修复方向**：reparse 抢占改为条件更新（仅 `INDEXED/FAILED/CHUNKED` 等非执行态可重置，执行态返回 409/404），或将抢占条件升级为带 token/版本号的 CAS；补"reparse 在执行中"集成测试。

## B2-3. run 滞留 QUEUED 无任何回收——巡检只扫 ACTIVE，重启/崩溃落在附件处理窗口即会话永久锁死

- **严重度**：高
- **置信度**：高
- **位置**：`backend/src/main/java/com/commerce/rag/worker/ChatRequestWorker.java:213-228`（sweepStaleRuns）、`:377-421`（附件处理在 ACTIVE 之前）、`:185-203`（stop 优雅关闭）；`service/impl/ChatRunServiceImpl.java:193-203`（findStaleActive 仅 ACTIVE）；`db/migration/V6__full_schema_v5.sql:281`（唯一索引含 QUEUED）
- **引入提交**：`0ffe128`（M-8 引入 ACTIVE 巡检；同提交波的 P3-2 裁决删除了 XCLAIM 重投机制）
- **问题描述与证据**：
  ```java
  // findStaleActive：只查 ACTIVE，QUEUED 永远不在巡检范围
  .eq(ChatRun::getStatus, "ACTIVE")
  .isNotNull(ChatRun::getStartedAt)          // startedAt 仅在转 ACTIVE 时写入（ChatRunServiceImpl:90-91）

  // 唯一索引：QUEUED 同样锁会话
  CREATE UNIQUE INDEX uniq_active_run_per_session ON chat_run(session_id)
      WHERE status IN ('QUEUED', 'ACTIVE') AND deleted = 0;
  ```
  以下三个窗口都会产生"滞留 QUEUED"（全仓 grep "QUEUED" 确认无任何回收/重投路径）：
  1. **附件处理窗口（最长、最现实）**：`processRequest` 中附件下载/VLM caption/文档 embedding（:377-390，`orchestrator.process`）发生在 `updateStatus(runId, "ACTIVE")`（:421）**之前**——run 全程保持 QUEUED。进程重启/崩溃/OOM 落在该窗口（可达数十秒），run 永久 QUEUED。
  2. **优雅停机丢弃排队任务**：`stop()` 先 `runPool.shutdown()` + 30s 等待再 `shutdownNow()`——仍排在 runPool 队列里未开始的任务被直接丢弃，对应 run 停留 QUEUED。**常规滚动重启即可触发**。
  3. **读后 ACK 前崩溃**：消息滞留 PEL 且 XCLAIM 重投已删（P3-2 裁决），run 同样停留 QUEUED。
- **影响**：滞留 QUEUED 的 run 永久占据 `uniq_active_run_per_session`，该会话后续所有 `chat()` 恒 409（ConcurrentRunException），仅能手工改库解锁——正是 M-8 注释自述要消除的"会话锁死"，但守卫只覆盖了 ACTIVE 半边。客户端侧同样表现为 B2-1 式的无限"生成中"（ring 已由入口创建，无终态事件）。
- **建议修复方向**：`findStaleActive` 扩展为同时扫"创建超过阈值的 QUEUED run"（如 `created_at < now-阈值` 置 ERROR）；或停机时对未执行任务回写 ERROR；`stop()` 丢弃队列任务前逐个置 ERROR。

## B2-4. 完成时刻 DB 故障残余路径：doOnComplete 抛出入 catch——双终态事件 + chat_message 重复落库（历史 P0-7/P1-5 残余）

- **严重度**：中
- **置信度**：高
- **位置**：`backend/src/main/java/com/commerce/rag/worker/ChatRequestWorker.java:467-490`（doOnComplete：先 persist 再 handleCompleted）、`:492-508`（catch：再 handleError + 再 persistMessages）、`:873-891`（updateStatusWithRetry 3 次耗尽后抛 IllegalStateException）；`db/migration/V6__full_schema_v5.sql:288-303`（chat_message 对 (run_id, seq) **无唯一约束**，仅普通索引）
- **关联历史**：08-15 清单 P0-7（重复持久化机制）与 P1-5（updateStatusWithRetry）——修复给 handleError 加了兜底 try/catch，但 doOnComplete→catch 的重复持久化路径未消除，属修复残余
- **问题描述与证据**：
  ```java
  .doOnComplete(() -> {
      ...
      persistMessages(...);                    // 第一次落库（成功）
      handleCompleted(runIdStr, runId, runState);   // push END(COMPLETED) 后 updateStatusWithRetry
      ...
  })
  .blockLast(Duration.ofMinutes(5));
  } catch (Exception e) {                       // handleCompleted 抛出 → blockLast 抛出 → 进入此分支
      errored.set(true);
      try { handleError(runIdStr, runId, runState, e); }   // 再推一个 ERROR 事件
      catch (Exception errorEx) { ... }
      persistMessages(...);                     // 第二次落库，无幂等防护
  }
  ```
  `updateStatusWithRetry`（P1-5 修复）3 次重试（含 1.5s 退避）耗尽后**故意上抛**（:890 注释"3 次仍失败上抛由调用方兜底"），异常经 doOnComplete → blockLast → catch 分支：① 客户端先收 END(COMPLETED) 又收 ERROR 双终态事件；② catch 分支无"已持久化"标志，若 DB 在 handleError 的重试窗口内恢复，`persistMessages` 二次成功 → 整批消息重复插入（chat_message 无 (run_id, seq) 唯一约束兜底）；③ run 终态被回写为 ERROR，与客户端已见 COMPLETED 矛盾。
- **影响**：历史回放/管理端会话详情出现成倍重复消息；前端状态机收到双终态。触发需完成时刻 DB 持续故障 ≥1.5s 后又恰好恢复，窗口窄但机制确凿（与 P0-7 同源同级别）。
- **建议修复方向**：引入 per-run `persisted` 原子标志（与 `errored` 同模式），catch 分支仅在未持久化时执行 persistMessages；或给 chat_message 加 (run_id, seq) 唯一部分索引作最终防线。

## B2-5. 四处多表级联软删无 @Transactional——中途失败留部分级联不一致

- **严重度**：中
- **置信度**：高
- **位置**：
  - `backend/src/main/java/com/commerce/rag/service/impl/ChatSessionServiceImpl.java:186-208`（deleteSession：message→run→session 三连 UPDATE，无事务）
  - `backend/src/main/java/com/commerce/rag/service/impl/CourseServiceImpl.java:232-295`（deleteCourse：content→schedule→teacher→enrollment→chunk→course 六连 UPDATE，无事务）
  - `backend/src/main/java/com/commerce/rag/service/impl/KnowledgeBaseServiceImpl.java:171-216`（delete：chunk→document→kb 三连 UPDATE）
  - `backend/src/main/java/com/commerce/rag/service/impl/DocumentServiceImpl.java:247-281`（delete：chunk→document 两连 UPDATE）
  - 对照组：`EnrollmentServiceImpl.addStudents:98` 与 `ChatMessageServiceImpl.batchInsert:47` 均正确标注 @Transactional（全 service 层仅此 4 处事务注解）
- **问题描述与证据**：以上级联均为多条独立 autocommit UPDATE。以 deleteSession 为例：`messageMapper.update`（软删消息）成功后 `runMapper.update` 抛异常（连接池耗尽/瞬时故障）→ 会话未删、run 未删、消息已删——管理端看到的会话详情消息数为 0 但会话仍存活。deleteCourse 同理可留下"课程已删而排期/选课仍 active"或反向的中间态。外部资源先行（MinIO/Milvus 先清理、失败上抛可重试收敛）是既有正确设计，但 **PG 侧多语句本身仍应原子**。
- **影响**：DB 中途故障留下跨表不一致的中间态；用户重试删除可收敛（幂等），但观察窗内管理端/学生端读到自相矛盾数据（如 chunk 已删而 doc 的 chunk_count 仍非 0）。违反工程宪法数据一致性要求（多表写应具原子性）。
- **建议修复方向**：四处级联软删方法补 `@Transactional`（均为 public、经接口代理调用、无自调用问题）；外部资源清理保持在事务外先行，事务仅包裹 PG 多表写。

## B2-7. cancel 无终态校验——对已终态 run 取消时 cancelFlags 条目永久泄漏

- **严重度**：低
- **置信度**：高
- **位置**：`backend/src/main/java/com/commerce/rag/stream/ChatStreamEntry.java:202-208`（cancel 仅归属校验，无 run.status 终态检查）；`backend/src/main/java/com/commerce/rag/worker/ChatRequestWorker.java:526-529`（cancelFlags.computeIfAbsent）与 `:511`（仅 processRequest.finally 清理）
- **问题描述与证据**：
  ```java
  public void cancel(String runId, HttpServletRequest httpRequest) {
      checkRunOwnership(runId, userId);        // 只查归属，不查 status
      worker.cancel(runId);                     // cancelFlags.computeIfAbsent(runId, ...).set(true)
  }
  ```
  对 COMPLETED/CANCELLED/ERROR 的 run 调 cancel（前端"停止生成"按钮在收尾时刻的重复点击即可触发）：processRequest 早已结束并 `cancelFlags.remove`，本次 `computeIfAbsent` 新建的条目**没有任何后续清理方**——`ConcurrentHashMap<String, AtomicBoolean>` 条目随每次此类调用累积。
- **影响**：小而确定的内存泄漏（每条目约百余字节 + runId 字符串）；认证用户可对自己历史 run 反复调用放大。
- **建议修复方向**：cancel 前校验 run 非终态（终态返回 200 幂等即可）；或 `worker.cancel` 仅当 `cancelFlags` 已存在条目时置位（`ifPresent` 语义），不新建条目。

## B2-8. check-then-insert 撞唯一索引竞态族——并发双击落 503 而非业务 409

- **严重度**：低
- **置信度**：高
- **位置**（同类模式多处，均"先查后插"且不捕获冲突异常）：
  - `backend/src/main/java/com/commerce/rag/service/impl/UserFeedbackServiceImpl.java:65-104`（selectOne 后 insert；唯一索引 `uniq_feedback_message(user_id, message_id)` V6:325）

  - `backend/src/main/java/com/commerce/rag/service/impl/SysUserServiceImpl.java:72-108`（用户名/超管查重后 insert；`uniq_sys_user_username` V6:115）
  - `backend/src/main/java/com/commerce/rag/service/impl/KnowledgeBaseServiceImpl.java:70-81`（create 无查重直插；`uniq_knowledge_base_name` V6:26，重名直接裸撞索引）
  - 仓库内正确范式对照：`ChatRunServiceImpl.createRun:61-77` 捕获 `DataIntegrityViolationException` 转 `ConcurrentRunException`（→409）
- **问题描述与证据**：以点赞为例——用户双击赞按钮，两请求并发 `selectOne` 均得 null → 双双 insert → 后者撞唯一索引抛 `DataIntegrityViolationException`（DataAccessException 子类）→ `GlobalExceptionHandler:54-55` 统一映射 **503**（"数据库服务异常"），而非语义正确的 409/更新成功。DB 约束兜底无数据损坏，属契约与体验缺陷。
- **影响**：并发提交下偶发 503（服务端错误语义），用户重试即走更新分支成功；无数据损坏。
- **建议修复方向**：统一按 createRun 范式捕获 `DataIntegrityViolationException` 转对应 BizException（409），或改用 `INSERT ... ON CONFLICT`（XML）/条件 insert。
