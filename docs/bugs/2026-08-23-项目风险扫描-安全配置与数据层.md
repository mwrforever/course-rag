## B1-1. PG 降级设备互踢把刚创建的 login_record 误判为旧设备——Redis 故障期间登录即自吊销

- **严重度**：高
- **置信度**：高
- **位置**：`backend/src/main/java/com/commerce/rag/auth/DeviceKickService.java:300-329`（kickAndLoginPgFallback）；`backend/src/main/java/com/commerce/rag/controller/AuthController.java:123-127`（先创建记录后互踢）；`backend/src/main/resources/mapper/SysLoginRecordMapper.xml:6-11`（selectActiveForUpdate 无排除条件）
- **问题描述**：
  登录流程先插入新的 ACTIVE login_record，再执行设备互踢。Redis 故障时互踢降级到 PG，`selectActiveForUpdate(userId, deviceType)` 按 `status='ACTIVE'` 查询，**刚插入的新记录也在结果集中**，且 `kickAndLoginPgFallback` 接收了 `newLoginId` 参数却完全未使用（无 `id != newLoginId` 排除），`oldRecords.get(0)` 取首条（无 ORDER BY，行序不确定）。
- **证据**：

  ```java
  // AuthController.login —— 步骤 6 先创建记录（自动提交，立即可见）
  Long loginRecordId = authSessionService.createLoginRecord(...);   // L123：插入 ACTIVE 新记录
  // 步骤 7 后互踢
  deviceKickService.kickAndLogin(user.id(), deviceType, jtiAt, jtiRt, loginRecordId);  // L127

  // DeviceKickService.kickAndLoginPgFallback（L303-324）—— newLoginId 形参从未使用
  List<SysLoginRecord> oldRecords = loginRecordMapper.selectActiveForUpdate(userId, deviceType);
  if (!oldRecords.isEmpty()) {
      SysLoginRecord oldRecord = oldRecords.get(0);        // 可能取到刚插入的新记录
      loginRecordMapper.updateStatusById(oldRecord.getId());            // 新记录被置 REVOKED
      addToBlacklistPg(oldJtiAt, "ACCESS", userId, null, "DEVICE_KICKED");  // 新 AT 入 PG 黑名单
      addToBlacklistPg(oldJtiRt, "REFRESH", userId, null, "DEVICE_KICKED"); // 新 RT 入 PG 黑名单
  }
  ```

  ```xml
  <!-- SysLoginRecordMapper.xml L6-11：无 id != #{newLoginId} 条件 -->
  SELECT ... FROM sys_login_record
  WHERE user_id = #{userId} AND device_type = #{deviceType} AND status = 'ACTIVE' AND deleted = 0
  FOR UPDATE
  ```

  完整故障链（Redis 故障、PG 正常——正是降级设计的核心场景）：
  1. 首次登录用户：无旧 ACTIVE 记录 → `oldRecords` 仅含刚插入的新记录 → **必然自踢**；已有会话用户：`get(0)` 行序不定，约半数场景踢中自己；
  2. 新 jtiAt/jtiRt 双双写入 PG 黑名单（`DEVICE_KICKED`），新记录置 REVOKED；
  3. 登录响应 200 返回新 Token，但 `isBlacklisted` 降级 PG `countByJti` 命中刚插入的行 → **下一个请求即 401「令牌已被吊销」**；refresh 同样被黑名单拦截 → 该次登录会话立即报废；
  4. Redis 恢复后该黑名单行仍生效（`isBlacklisted` Redis miss 后无条件降级查 PG，且 countByJti 不过滤 expires_at，见 B1-4）→ 用户须重新登录获得新 jti 才能恢复。

  对照：Redis 成功路径 `kickPgAudit` 按 `jti_at` 精确匹配旧记录（`updateStatusByUserAndJtiActive`），不受影响；单测 `DeviceKickServiceTest.kickAndLoginPgFallback_noOldRecord_notKicked` mock 了空列表场景，与生产「先插入后互踢」的真实时序不符，掩盖了该缺陷。
- **Commit 取证**：PG 降级互踢逻辑随 `4defa1f`（S2-2，JdbcTemplate 版本，7a1cbcb 迁移 XML 保持语义）引入；`1140da3`（S2-1 下沉 AuthSessionService）固化「先 createLoginRecord 后 kickAndLogin」顺序。历次审查（08-14/08-15/08-16）均未报告此项。
- **影响**：Redis 故障期间登录链路完全不可用（每次登录立即自吊销，响应却是成功），并批量产生永久生效的 PG 黑名单脏行；与降级设计目标（Redis 不可用时登录可用）直接矛盾，属 fail-closed 过度的认证可用性缺陷。
- **建议修复方向**：`selectActiveForUpdate` 增加 `AND id != #{newLoginId}` 排除当前登录记录（参数已存在，一行 SQL 的事）；或调整登录顺序为先互踢后创建记录。补「Redis 故障时登录成功且新 Token 可用」的集成测试。

## B1-2. RT 旋转后 login_record 更新静默失败即永久脱节，黑名单吊销体系对该用户失效；refresh 不校验用户禁用状态

- **严重度**：中
- **置信度**：高（机制逐行确凿；实际触发依赖一次 DB 瞬时故障窗口）
- **位置**：`backend/src/main/java/com/commerce/rag/auth/AuthSessionService.java:90-106`（updateLoginRecordOnRefresh 失败仅 warn）；`backend/src/main/java/com/commerce/rag/controller/AuthController.java:186-189`（refresh 不校验 status）；`auth/DeviceKickService.java:439-441`（disableUser 吊销依据）
- **问题描述与证据**：

  ```java
  // AuthSessionService.updateLoginRecordOnRefresh（L91-105）：按旧 jti_rt 定位更新，失败仅 warn 无补偿
  try {
      LambdaUpdateWrapper<SysLoginRecord> wrapper = Wrappers.<SysLoginRecord>lambdaUpdate()
              .eq(SysLoginRecord::getUserId, userId)
              .eq(SysLoginRecord::getJtiRt, oldJtiRt)   // ← 一旦脱节，此后每次都用最新 oldJtiRt 匹配，恒 0 行
              ...
  } catch (Exception e) {
      log.warn("刷新时更新 login_record 失败: ...", e);   // 无重试、无重放、无告警升级
  }
  ```

  ```java
  // AuthController.refresh（L187-189）：取最新角色但不校验用户状态（对照 login L106-108 有 ACTIVE 校验）
  UserDTO userDto = sysUserService.findById(userId);
  String role = userDto.role();        // 禁用用户（DISABLED）照样发新 AT/RT
  ```

  脱节链路：某次 refresh 时 DB update 瞬时失败（仅 warn）→ 记录停留在旧 jtiRt_old1，用户实际持有 old2 → 此后每次 refresh 按 `eq(jtiRt, oldN)` 定位恒不匹配 → 更新恒 0 行（静默）→ **脱节不可自愈**。脱节后三类吊销全部落空：
  1. `revokeOnLogout`（登出）：按 userId+ACTIVE 取记录的 jtiRt_old1 入黑名单——用户实际持有的 RT 不被吊销；
  2. `disableUser`（禁用/删除用户）：吊销 `selectActiveByUserId` 记录中的 jti——同样吊销不到实际持有的 RT；
  3. 叠加 refresh 不校验 `user.status`：被禁用的用户只要 RT 未入黑名单，即可无限旋转续命（AT 每 15min 换新，`AuthInterceptor` 也不查 status），「禁用」对该用户永久失效。
- **Commit 取证**：`de74a5e`（S2-1）引入 updateLoginRecordOnRefresh 及 try/catch 降级结构；refresh 主流程（含无状态校验）自 `556c00d` 时代延续至今。
- **影响**：纵深防御缺失（fail-open 方向的权限残留）。触发需一次 DB update 瞬时故障（或记录被并发 REVOKED），窗口存在但非高频；一旦发生即永久化且无任何告警。
- **建议修复方向**：① refresh 按记录定位失败（update 返回 0 行）或查询不到 ACTIVE 记录时拒绝刷新（fail-closed）或强制重新登录；② refresh 增加 `user.status == ACTIVE` 校验（与 login 对齐）；③ update 失败改 warn + 计数告警，避免静默。

## B1-4. sys_token_blacklist 无清理任务且 countByJti 不过滤 expires_at——表无限增长（历史挂账未修）

- **严重度**：低
- **置信度**：高
- **位置**：`backend/src/main/resources/mapper/SysTokenBlacklistMapper.xml:6-8`（countByJti）；全仓无任何黑名单删除/清理路径（grep `delete|clean|purge` 于该表零命中）
- **问题描述与证据**：

  ```xml
  <!-- 不过滤 expires_at：行即使已过 token 原始有效期仍计数生效 -->
  SELECT COUNT(*) FROM sys_token_blacklist WHERE jti = #{jti} AND deleted = 0
  ```

  写入方遍布全链路：每次 refresh 旋转（TOKEN_REUSE 行）、每次互踢（DEVICE_KICKED 双行）、禁用/删除用户（USER_DISABLED 批量行）、登出（MANUAL_REVOKE 双行）——**无任何定时清理、无逻辑删除调用、无 TTL**。每次登录/刷新至少新增 1~3 行，表单调增长；配合 B1-1 的自踢脏行，被错误写入的黑名单永久生效（countByJti 不过期）。
- **历史挂账标注**：该项为 **2026-08-16 BUG-1 的组成部分残留**——BUG-1 描述明确指出「该 PG 行无清理任务、countByJti 不过滤过期时间」，但修复（commit `0ffe128`）只恢复了 fail-open 语义（降级不写黑名单），表膨胀与查询不过期两点未修，故标注「历史挂账未修（原编号 2026-08-16 BUG-1）」。
- **影响**：长期运行表无限膨胀；过期黑名单行持续参与每次认证降级查询（PG 全表按 jti 索引扫描，性能影响可控但语义失真）。jti 为一次性随机值不会复用，无直接安全放大面。
- **建议修复方向**：定时任务清理 `expires_at < now()` 的行；countByJti 增加 `AND expires_at > now()`（注意与 B1-1 修复联动验证降级链路）。

## B1-5. RerankService 调用 @Deprecated record 组件 source()，违反「禁用弃用 API、警告清零」宪法

- **严重度**：低
- **置信度**：高
- **位置**：`backend/src/main/java/com/commerce/rag/retrieval/RerankService.java:154`（`original.source()`）；`backend/src/main/java/com/commerce/rag/bot/tool/dto/KnowledgeSearchResult.java:34`（组件声明）
- **问题描述与证据**：

  ```java
  // KnowledgeSearchResult.KnowledgeChunk（L34）：组件显式标记 @Deprecated
  public record KnowledgeChunk(
          String chunkId,
          String content,
          @Deprecated String source,      // 注释自述「new schema has no source field; currently set to empty string」
          ...)

  // RerankService.rerankSingle（L151-158）：跨包调用弃用 accessor 透传构造新 record

          original.chunkId(),
          original.content(),
          original.source(),     // ← 跨包调用 @Deprecated accessor，产生编译期 deprecation 警告
          ...);
  ```

  工程宪法明文「整个 Java 程序禁止使用任何被标记 @Deprecated 的方法/类……编译期 deprecation 警告必须清零」。`SearchKnowledgeTool.java:315` 构造时位置传参 `""` 不触发警告，但 RerankService 的 accessor 调用构成实际违例；该字段注释自认已废弃恒空串，属死字段延续。
- **Commit 取证**：`source` 字段废弃标注随 S1 计划 1/5（sha256 字段引入、docTitle 替代 source）落地。
- **影响**：运行无影响（恒空串透传）；属可验证的宪法违规 + 死代码延续（record 8 字段中 1 个已无语义）。
- **建议修复方向**：删除 `source` 组件（连同两处构造/accessor 调用同步清理），完成 docTitle 替代的收尾；若暂保留需按宪法附带 `TODO(标注预期清理版本)`。
