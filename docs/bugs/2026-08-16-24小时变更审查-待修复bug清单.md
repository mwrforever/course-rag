### BUG-1（中）179881e：Lua RT 一次性旋转的 Redis 降级路径"自拦截"——Redis 故障时 refresh 必 401 且 RT 被永久烧毁

- **提交**：`179881e`（fix: P3 A11 RT 一次性旋转原子化）
- **证据**：
  - `backend/src/main/java/com/commerce/rag/auth/DeviceKickService.java:209-216`（catch 分支）：
    ```java
    } catch (Exception e) {
        log.warn("Redis RT 原子标记失败，降级放行并写 PG 黑名单: jtiRt={}", jtiRt, e);
        addToBlacklistPg(jtiRt, "REFRESH", null, null, "TOKEN_REUSE");   // 先写 PG 黑名单
        return true;                                                     // 注释声称"放行"
    }
    ```
  - `backend/src/main/java/com/commerce/rag/controller/AuthController.java:172-181`：`markRefreshTokenUsedAtomic` 返回 true 后**紧接着**执行 `isBlacklisted(oldJtiRt)`。
  - `backend/src/main/java/com/commerce/rag/auth/DeviceKickService.java:168-191`（isBlacklisted）：Redis `hasKey` 异常 → 降级 `tokenBlacklistMapper.countByJti(jti)`（`SysTokenBlacklistMapper.xml:6-9`：`COUNT(*) WHERE jti=? AND deleted=0`，**不过滤 expires_at**）→ 刚插入的行立即可见 → 返回 true。
- **问题链**（Redis 故障、PG 正常——恰是降级设计的核心场景）：
  1. 步骤 3 `markRefreshTokenUsedAtomic`：Lua 执行抛异常 → catch → **写 PG 黑名单**（expires_at = now + refreshTokenExpiry）→ 返回 true（放行）；
  2. 步骤 4 `isBlacklisted`：Redis 查询也抛异常 → 降级 PG → **查到自己刚写入的行** → 401 "Refresh Token 已被吊销"。
  - 结果：Redis 故障期间**每一次 refresh 都 401**，降级完全失效；且该 PG 行无清理任务、countByJti 不过滤过期时间 → **RT 被永久烧毁**（即使 Redis 恢复，同一 RT 重试仍被拒）。
- **旧代码（179881e^）对比**：旧流程顺序为 ①`isRefreshTokenUsed`（降级查 PG 无行→放行）→ ②`isBlacklisted`（无行→放行）→ ③`markRefreshTokenUsed`（降级写 PG 黑名单→放行）。**写黑名单发生在黑名单检查之后**，Redis 故障时 refresh 成功（fail-open）。179881e 合并"检查+置位"为单 Lua 后，降级分支把"写 PG 黑名单"提前到了 isBlacklisted 之前，自拦截。
- **测试未覆盖原因**：`DeviceKickServiceTest.markRefreshTokenUsedAtomic_redisFail_fallbackOpen` 只断言方法级返回值 true，未覆盖 AuthController 层的 isBlacklisted 交互。
- **修复建议**：降级分支不写 TOKEN_REUSE 黑名单行（或先完成黑名单检查再写），恢复旧 fail-open 语义；补一个 AuthController 层"Redis 故障时 refresh 成功"的测试。
- **核实人**：主 agent 已对照 179881e^ 旧代码逐行确认顺序颠倒属实。

### BUG-3（低）64096a6：ChatController 409/503 错误响应体 wire-format 变化（跨端兼容待确认）

- **证据**：ChatController 删除局部 `@ExceptionHandler(ConcurrentRunException/DataAccessException)`（原返回 `Map.of("error","CONFLICT","message",...)`），改由 `GlobalExceptionHandler` 统一返回 `ApiResponse{code,message,data}`；409 文案从「该会话已有正在进行的对话」变为「会话 {sessionId} 已有活跃的 Run，无法创建新 Run」。HTTP 状态码不变（仍 409/503）。
- **性质**：提交说明声明"消除 Map 双轨"为有意为之，且新形态与全站 ApiResponse 契约一致——但这是对外可见的契约变化，**仓库内无前端代码可验证消费方**（前端不在本仓库）。若前端按 `body.error=="CONFLICT"` 或固定文案判断并发冲突会失效。证据不足判定为 bug，列为待确认项：需与前端确认消费方后再定。
- **核实人**：主 agent 确认 diff 属实，docs/ 无前端契约文档描述该响应体消费方式。

### BUG-4（低）64096a6：saveBatch 替代 XML 多值 INSERT 后，token_count 由显式 NULL 变为 DEFAULT 0

- **证据**：`ChatMessageServiceImpl.batchInsert`（:43-55）改 `this.saveBatch(messages)`（MP 默认 NOT_NULL 字段策略，null 字段不插入）；原 97c27ef XML 显式插 `#{m.tokenCount}`（null → NULL）；`V6__full_schema_v5.sql:290` token_count 有 `DEFAULT 0`。worker 全链路构造 ChatMessage 均不设置 tokenCount（`ChatRequestWorker.java:473-609` 已验证）。
- **影响**：chat_message.token_count 读回值由 NULL（未统计）变 0（计费为零），未来对 token_count 做 SUM/AVG 聚合或 NULL 判断语义不同。当前无消费方依赖，影响面小。
- **修复建议**：如须保持 NULL 语义，可在 batchInsert 内显式置 null 列（或字段注解 FieldStrategy），或接受 0 语义并记录决策。

### BUG-5（低）8395c1a：toDTO(course, false) 关联字段由 null 变为空列表，E2/E3/E8 响应 JSON 变化

- **证据**：`CourseServiceImpl.toDTO`（:429-440）includeRelations=false 时传 `List.of()`；旧手写实现（8395c1a^ `CourseService.java:416-418`）传 null。MapStruct 生成实现将空列表映射为空列表（不会变 null）→ 响应 JSON 从 `"contents": null` 变为 `"contents": []`。
- **影响面**：AdminCourseController E2 列表、E3 创建、AdminEnrollmentController E8 学生课程。前端以 `course.contents` 的 null 判断"详情未加载"会走到空数组分支（JS 中 `[]` 为 truthy）。多数迭代渲染反而更安全，低风险。
- **修复建议**：与前端确认消费方式；如须保持 null，转换器按 includeRelations 语义处理。

### BUG-6（低）e00a84c：J4 chunkContext 的 parent/prev/next 与 J7 createSession 的 lastMessageAt 由"缺失 key"变为 null 字段

- **证据**：StudentController J4 旧代码 `if (parent != null) result.put("parent", ...)`（关联不存在时无此 key），新 `ChunkContextVO` record 恒输出 `"parent": null`；J7 旧 Map 无 lastMessageAt key，新 `SessionVO` 恒输出 `"lastMessageAt": null`。

### BUG-7（低）23f3309 基线：application.yml 硬编码默认 JWT 密钥与中间件口令（安全提醒）

- **证据**：`backend/src/main/resources/application.yml`：`auth.secret: ${JWT_SECRET:commerce-rag-secret-key-2026-must-be-at-least-256-bits-long-for-hs256}`、`spring.datasource.password: ${PG_PASSWORD:rag_pg_2024}`、`spring.data.redis.password: ${REDIS_PASSWORD:rag_redis_2024}`、`minio.secret-key: ${MINIO_SECRET_KEY:rag_storage_2024}`。

### BUG-9（低）d9b782a：@Qualifier 留在 final 字段上，@RequiredArgsConstructor 不复制注解，依赖 Spring 参数名匹配

- **证据**：无 `lombok.config`（`lombok.copyableAnnotations` 未配置），`DocumentServiceImpl.java:58` 等 5 处 `@Qualifier("etlPool"/"dashboardStatsCache"/"courseQueryCache")` 注解不会随 Lombok 生成的构造器参数携带；Spring 构造器注入按类型解析多 Bean（etlPool/runPool、两个 Cache）时回退**参数名匹配**（编译带 -parameters，参数名==字段名==Bean 名）才得以正确注入。

- **修复建议**：在构造器参数上显式写 @Qualifier（如 ChatRequestWorker:99 的正确写法），或配置 lombok.copyableAnnotations。

### BUG-11（低）23f3309 基线：WarningHook per-thread 检测状态在取消/异常路径不清理

### BUG-12（低）64096a6：ChatMessageServiceTest 删除 ID 非空断言，saveBatch 雪花 ID 填充失去单测保护
