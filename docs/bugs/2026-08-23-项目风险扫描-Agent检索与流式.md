## B3-1. ETL Milvus 插入失败吞异常——文档误标 INDEXED、向量永久缺失漏召回（历史挂账未修）

- **严重度**：高
- **置信度**：高
- **位置**：`backend/src/main/java/com/commerce/rag/etl/EtlPipeline.java:809-820`（insertToMilvusBatch 吞异常）；受影响调用点 `:562`（embedAndIndex）、`:621`（reEmbedAndUpsert）、`:783`（syncDocToMilvus）、`:793`（syncChunkRowToMilvus）
- **类别**：数据丢失（Milvus/PG 不一致）
- **历史挂账**：08-14 清单 P2-1b（`2026-08-14-ETL幂等性与流泄漏.md` Bug 2）明确记录「Milvus 删除/插入失败被吞 → PG 新内容 + Milvus 旧内容」。后续修复波只修了 **delete** 路径（P0-8：`deleteFromMilvusByChunkId` 等改为失败上抛），**insert** 路径未同步修复，残留至今。
- **问题描述与证据**：

  ```java
  // EtlPipeline.java L809-820：插入失败仅记 warn，异常不上抛
  private void insertToMilvusBatch(List<JsonObject> rows) {
      ...
      try {
          milvusClientV2.insert(insertReq);
      } catch (Exception e) {
          log.warn("Milvus 批量插入失败: 行数={}, error={}", rows.size(), e.getMessage());
      }
  }
  ```

  与同文件 P2-1/P2-6 修复设计直接矛盾——`embedAndIndex`（L565-571）批次 catch 仅覆盖「embed 抛异常/PG 回写抛异常」，`insertToMilvusBatch` 内部吞掉 Milvus insert 异常后 `failedCount` 不增加，L573-587 照常判定：

  ```java
  // L573-587：failedCount==0 → updateDocStatus(docId, "INDEXED", null)
  if (failedCount > 0) { ... updateDocStatus(docId, "FAILED", ...); return; }
  updateDocStatus(docId, "INDEXED", null);
  ```

  触发时序：Milvus 瞬时不可用 → 开头 `deleteFromMilvusByDocId`（L518，上抛型删除在 Milvus 恢复窗口内成功或整批直接失败）成功删除旧向量 → 各批 embed 成功 + PG 向量回写成功 + Milvus insert 全部失败被吞 → 文档标 **INDEXED（绿）**，但 Milvus 中该文档**零向量**。
- **Commit 证据**：现行批量形态由 `0ffe128`（H-3 批量向量化改造）引入；吞异常语义继承自 08-14 基线（P2-1b 记录在案）。
- **影响**：
  1. `process()` 状态守卫（L138-148）仅允许 PENDING/FAILED 抢占——INDEXED 文档无法自动重跑，B 端看到绿色状态不会主动 reparse，该文档在学生端**永久漏召回**且无任何告警/重试路径（P2-6 注释自述最担心的「fail-closed 漏召回」场景恰被 insert 吞异常重新打开）；
  2. `reEmbedAndUpsert`（B 端分片内容编辑，L620-621）：delete 成功 + insert 失败被吞 → 该 chunk 向量从 Milvus 消失，PG 内容已更新，检索与库内分裂且无状态标记；
  3. `syncDocToMilvus`/`syncChunkToMilvus`（课程标注同步，L777-783）：批量 delete 后 insert 失败被吞 → 同步后向量反而丢失。
- **建议修复方向**：`insertToMilvusBatch` 失败上抛（对齐 P0-8 对 delete 的处理哲学）——embedAndIndex 调用点既有批次 catch 会将其计入 `failedCount` → 走 FAILED + P2-6 清理 + 可重跑收敛；reEmbedAndUpsert/syncDocToMilvus 调用点上抛阻断调用方并保留可重试语义。

## B3-2. 附件 objectKey 客户端可控且下载无归属校验——可直读 MinIO 同 bucket 任意对象

- **严重度**：中
- **置信度**：高
- **位置**：`backend/src/main/java/com/commerce/rag/service/impl/AttachmentServiceImpl.java:103-111`（download 无任何校验）；`dto/ChatRequest.java:14`（attachments 客户端任意构造）；`service/AttachmentOrchestrator.java:60`（url 直接透传下载）
- **类别**：越权/注入攻击面（纵深防御缺失）
- **问题描述与证据**：

  ```java
  // AttachmentServiceImpl.download：objectKey 原样直读，无前缀/归属/存在性校验
  public byte[] download(String objectKey) {
      try (InputStream in = minioStorageService.downloadFile(objectKey)) {
          return in.readAllBytes();
      } ...
  }
  ```

  链路：`POST /api/v1/student/chat` 请求体 `attachments[].url` 完全由客户端控制 → `ChatRequestWorker.processRequest` 原样入队 → `AttachmentOrchestrator.process` → `attachmentService.download(att.url())` → MinIO `getObject(objectKey)`，**无任何校验**：
  1. 不校验前缀（附件区固定 `0/{uuid}.{ext}`，见 `uploadSingle` L121 与类注释「kbId 固定传 0L」）；
  2. 不校验该 url 是否由当前用户/当前会话上传（无「附件 url ↔ 用户」绑定表，attachments_json 只随消息落库不回查归属）。

  而附件与 B 端知识库文档**共用同一 bucket**（`minio.bucket` 单一配置，知识库 objectKey 为 `{kb_id}/{uuid}.{ext}`，见 `MinioStorageService.buildObjectKey` L181-183）：学生构造 `attachments=[{"type":"document","url":"<知识库objectKey>",...}]` 即可让 worker 下载任意知识库文档原文，经 `AttachmentDocumentProcessor` 解析后作为 `<user-document>` 注入自己会话的模型上下文——绕过知识库/文档归属校验体系（P0-2 教师越权修复只覆盖 B 端管理接口）。
- **Commit 证据**：编排链路 `082c4f1`（feat(S1): 附件编排与 QU caption 拼装）引入；download 无校验形态自始如此。
- **利用前提与影响**：objectKey 含 32 位 hex uuid 不可枚举，且 `DocumentVO` 已声明 sourcePath 不外暴露——实际利用需目标 objectKey 经由其它途径泄露（日志、URL 分享、未来某接口回显）。属「objectKey 即唯一凭证」设计下的纵深缺失：一旦 key 泄露即等同内容越权读取，且读取行为发生在服务端（无访问日志关联）。学生间互用附件 url 同理可让他人会话解析自己的附件（低危害）。
- **建议修复方向**：`download` 前置校验 objectKey 以 `0/` 前缀开头（附件区隔离）；更完整的方案是上传时记录「附件 url ↔ userId」映射（或 uuid 内嵌 userId 分段），worker 消费时校验归属，拒绝即跳过该附件。

## B3-3. 检索 `<document>` 块「来源文档」恒为「未知」——docTitle 从未填充，偏离 spec §3.2

- **严重度**：中
- **置信度**：高
- **位置**：`backend/src/main/java/com/commerce/rag/bot/tool/SearchKnowledgeTool.java:316`（构造传空串）；`retrieval/ContextBuilderService.java:79-83`（输出「来源: 未知」）；`bot/tool/dto/KnowledgeSearchResult.java:25`（注释声称未实现）
- **类别**：S1 实现偏离已批准 spec
- **问题描述与证据**：

  spec §3.2 定稿（`2026-08-12-multimodal-rag-design.md` L162）：`[1] 系统知识库 chunk 内容(元数据:来源文档/章节/课程)`——要求 document 块内每条引用标注**来源文档**。实现中：

  ```java
  // SearchKnowledgeTool.java L316：docTitle/source 两参恒传空串（新 schema 无 source 字段）
  chunks.add(new KnowledgeChunk(
          chunkId, content, "", "", headingPath, score, null, sha256.isBlank() ? null : sha256));

  // ContextBuilderService.java L79-83：空串经 blankTo 兜底为「未知」
  sb.append("  (来源: ").append(blankTo(c.docTitle(), "未知")).append(" / 章节: ")
          .append(blankTo(c.headingPath(), "未知")).append(")\n");
  ```

  `KnowledgeChunk.docTitle` 的 javadoc（L25）自述「从 PG document.title 关联查询，替代已废弃的 source 字段」——但全链路检索后**从未做该关联查询**（Milvus knowledge_chunks schema 无 doc_title 字段，`OUTPUT_FIELDS` 亦无；doc_id 已取回但未用于回查 PG）。结果：所有检索注入的资料来源恒显示 `(来源: 未知 / 章节: xxx)`。
- **Commit 证据**：`23t3309`（基线提交）即此形态；`fcd1085`（SHA256 去重重构）延续空参构造。
- **影响**：
  1. 模型侧失去引用溯源能力——回答无法提及资料出自哪份文档，引用标注「资料 [N]」的来源不可解释（spec §3.2 同页「引用规则：系统资料标注资料 [N]」的可解释性目标落空）；
  2. 学生侧无法验证资料权威性；B 端排障（哪份文档命中）只能靠 headingPath 猜。
- **建议修复方向**：检索结果按已取回的 `doc_id` 批量回查 PG document.title（一次 `in` 查询 + `Wrappers.lambdaQuery` 按需取列，回填 KnowledgeChunk.docTitle）；或在 ETL 写入 Milvus 时冗余 doc_title 标量字段（schema 演进需评估 initializer drop 重建影响）。

## B3-4. 附件局部检索 embed 异常无降级捕获——embedding 故障时带文档附件的 run 整体 ERROR

- **严重度**：中
- **置信度**：高
- **位置**：`backend/src/main/java/com/commerce/rag/bot/graph/RetrieveNode.java:199-200`（supplyAsync 提交）、`:218-219`（join 无异常隔离）、`:379`（embed 裸调用）
- **类别**：运行错误（降级承诺失效）
- **问题描述与证据**：

  RetrieveNode 类注释（L81-84）承诺：「失败降级：检索异常 → 不写 document，ReactAgent 直接回答并记日志」。三段并行任务中 episodic 召回（`recallEpisodic` 内部全 catch）、知识检索（`searchSingle` L322-325 全 catch）均有降级，唯独**附件局部检索向量计算无任何捕获**：

  ```java
  // L199-200：任务提交（无 exceptionally/whenComplete 兜底）
  CompletableFuture<String> userDocFuture = CompletableFuture.supplyAsync(
          () -> buildUserDocumentText(attachmentContext, originalQuery), retrieveExecutor);
  ...
  // L218-219：join 直接抛 CompletionException → apply 异常完成 → 图执行失败 → run ERROR
  List<KnowledgeChunk> chunks = chunksFuture.join();
  String userDocument = userDocFuture.join();

  // L379：buildUserDocumentText 内 embed 裸调用，无 try-catch
  float[] queryVector = embeddingModel.embed(originalQuery);
  ```

  触发条件：用户带**文档附件**提问（`AttachmentContext.documents()` 非空——注意 `AttachmentOrchestrator.process` L66 即使解析失败返回空列表也会 put 进 map，key 存在即触发 embed）+ 意图为 knowledge_question + embedding 服务异常（超时/限流/故障）→ `userDocFuture.join()` 抛出 → `processRequest` 走 onErrorResume → run ERROR、SSE error 事件、无任何回答。
- **Commit 证据**：`3b86775`（2-3 三段并行化）引入并行形态并在注释中自认「附件 embed 异常与改造前同步路径等价地向上传播」——等价传播恰恰保留了缺陷（改造前同步路径同样无捕获，最早可溯至附件链路引入提交）。
- **影响**：与 spec §5.1/§5.4「附件单项失败跳过不中断对话」的边界设计矛盾——embedding 故障期间，**无附件用户的提问仍能正常回答**（知识检索内部自嵌也失败但被 catch，降级直答），而带文档附件的用户提问直接 run ERROR。故障面被附件放大而非隔离。
- **建议修复方向**：`buildUserDocumentText` 内对 `embeddingModel.embed` 包裹 try-catch（异常/空向量返回 null，走既有「无 user-document 子块」路径）；或 `userDocFuture.exceptionally(e -> null)` 统一降级。与同文件 `embedSafely`（L318-326，预嵌入的降级先例）保持同款语义即可。

## B3-6. WarningHook fallbackWarnings 组件级全局缓冲——降级路径写入的安全告警可跨用户串扰

- **严重度**：低
- **置信度**：中（机制确定，触发依赖 updateState 降级路径）
- **位置**：`backend/src/main/java/com/commerce/rag/bot/hook/WarningHook.java:74`（组件级 CopyOnWriteArrayList）、`:432-446`（writeWarning 降级写入）、`:477-480`（drainWarnings 降级读取）
- **类别**：跨用户隔离缺失（内容为系统告警，非用户数据）
- **问题描述与证据**：

  ```java
  // L74：组件级单例缓冲，非 per-thread/per-run
  private final List<String> fallbackWarnings = new CopyOnWriteArrayList<>();

  // L432-446：updateState 抛异常（如 PostgresSaver DB 故障）→ 写入全局缓冲
  // L477-480：任意 run 的 beforeModel 读空自家 state 后兜底取走全局缓冲并注入对话
  if (warnings.isEmpty() && !fallbackWarnings.isEmpty()) {
      warnings.addAll(fallbackWarnings);
      fallbackWarnings.clear();
  }
  ```

  writeWarning 与 drainWarnings 无任何 runId/userId 关联：用户 A 的 run 在 `updateState` 失败时降级写入的告警（内容如「Token 预算告警/循环检测」），会被**任意其它用户**下一个执行 beforeModel 的 run 取走，以 `⚠️ [...]` UserMessage 注入其模型上下文。
