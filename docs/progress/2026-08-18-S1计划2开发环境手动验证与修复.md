## 3. 发现并修复的 Bug（3 个）

### Bug-1（已修复）：Tika 2.9.2 PDF 图片提取完全失效

- **现象**：上传含内嵌图片 PDF，日志恒为「捕获图片数=0」，图片分片永远不产生
- **根因（字节码实锤）**：`PDFParserConfig.extractInlineImages` 默认 false，`PDF2XHTML.extractImages` 入口直接 return（ImageGraphicsEngine 不运行，XObject 图片也不提取）；`imageStrategy` 默认 NONE
- **修复**：`EtlPipeline.parseDocument` 显式设置 `setExtractInlineImages(true)` + `setImageStrategy(RAW_IMAGES)`
- **测试**：新增 `PdfImageExtractionTest`（真实含图 PDF fixture `src/test/resources/etl/higher-math-with-image.pdf`，断言图片捕获 + XHTML img + 中文正文）
- **影响面**：计划 1/5（ETL 多模态底座）引入，图片链路从未真实生效；本次手动验证首次暴露

### Bug-2（已修复）：caption 图片调用走 text-generation 接口报「url error」

- **现象**：caption 调用 DashScope 报 `HTTP 400 url error, please check url`
- **根因（字节码实锤）**：SAA 1.1.2 的 `DashScopeChatModel` 按 `ChatCompletionRequest.multiModel` 路由——`multiModel=false`（默认）走 `/text-generation` 接口，图片 data URL 被当 URL 解析报错；图片只能走 `/multimodal-generation` 接口
- **修复**：`ImageCaptionService` 的 `DashScopeChatOptions` 加 `.multiModel(true)`
- **测试**：`ImageCaptionServiceTest` 2 用例保持全绿（mock 路径不受影响）
- **排查过程**：本地 HTTP 代理（chunked 解析）抓取真实请求体 → 与 curl/python 直测对比（原生 vs 兼容接口）→ 反编译 SAA 字节码定位 multiModel 路由

### Bug-3（已修复，临时降级）：milvus-sdk-java EmbeddedText sparse 检索不可用

- **现象**：检索时 Milvus 客户端无限重试（RpcUtils Retry 至 75 次/210 秒），最终「并行检索超时」→ 检索结果恒为空
- **根因**：milvus-sdk-java 2.6.11（及 2.6.21）的 `EmbeddedText` 在 sparse/混合检索与服务端 BM25 Function 不兼容（GitHub issue milvus-io/milvus-sdk-java#1402，仍 Open）；pymilvus 同请求正常。服务端要求「BM25 Function 检索必须传 varchar/text」，但 Java SDK 发送的 EmbeddedText 触发服务端内部错误（可重试错误码）→ SDK 无限重试后静默返回 null（2.6.21 才改为抛异常）
- **修复**：`SearchKnowledgeTool` 加 `retrieval.sparse-enabled` 开关（默认 false）——关闭时只发 dense 单路（HybridSearchReq 单请求，验证 1.6s 正常）；SDK 修复后置 true 恢复全文检索
- **测试**：`SearchKnowledgeToolTest` 原「双路」用例改为「sparse 关闭时单路」+ 新增「sparse 开启时双路」（23 用例全绿）
- **注意**：这是**降级修复**（丢全文检索能力），正式方案（应用侧 sparse 向量/服务端改造/等 SDK 修复）需用户决策

### Bug-4（已解决，30f5738 用户裁决实施）：SAA 1.1.2 与 qwen3.x 新模型不兼容

- **现象**：主对话（qwen3.8-max）/QU（qwen3.7-flash）文本任务报 `400 url error`；caption（多模态）修复后正常
- **根因（实测实锤）**：兼容模式模型列表确认 `qwen3.8-max`/`qwen3.7-flash` 为有效模型 ID，但 DashScope **原生 text-generation 接口对它们一律 url error**（同一 key 下 qwen-max 旧模型正常）；SAA 1.1.2 的 DashScopeChatModel 硬编码走原生接口（1.1.2.2 反编译确认未修复）
- **解决方案（用户 2026-08-18 裁决："统一使用 openai 协议的兼容端口"）**：chat 全通道切换 Spring AI OpenAI ChatModel（base-url=`https://dashscope.aliyuncs.com/compatible-mode`，Spring AI 自动补 `/v1/chat/completions`）：
  - pom 加 `spring-ai-starter-model-openai`（BOM 管版本）
  - `spring.ai.model.chat=openai`（Spring AI 通用 provider 选择，DashScope chat 自动配置因 havingValue 不匹配停用，消除双 ChatModel bean）；`spring.ai.model.embedding/rerank=dashscope`（保留 SAA 原生通道）
  - 主对话（LeadAgentGraph）/QU（QueryUnderstandingService）/摘要（CustomSummarizationHook）/caption（ImageCaptionService）四处 `DashScopeChatOptions` → `OpenAiChatOptions`（`.withModel()` → `.model()`）；caption 不再需要 multiModel（兼容端点原生支持视觉）
  - 测试同步：QueryUnderstandingServiceTest/ImageCaptionServiceTest 的 options 断言 + application-test.yml 加 openai 段（dummy key）
- **dev 实测（默认配置，无任何环境变量覆盖）**：qwen3.8-max 知识问答完整跑通（QU `filters=[高等数学]` 课程名提取生效 → CourseNameMapper 映射 → 检索精排 1 条 → document 注入 697 字符 → **回答正确标注"资料 [1]"**——qwen3.8-max 遵循引用协议，顺带解决 qwen-max 不标注问题）
- **连带收益**：之前遗留的「课程名过滤路径」「资料 [N] 标注」两项验证在模型通道切换后全部通过
