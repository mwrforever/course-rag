## 一、R0：Jackson Long → String 全局序列化（阻断级，新发现）

### 问题

全工程无任何 Jackson Long 序列化定制（config/ 16 文件无 JacksonConfig、无 ToStringSerializer、yml 无 spring.jackson 段）。雪花 ID 19 位超出 JS `Number.MAX_SAFE_INTEGER`（2^53-1），以 JSON number 下发**必然精度丢失**，前端拿到错位 ID（反馈 messageId、会话 id、分片 id 全部受影响）。

### 方案

新建 `config/JacksonConfig.java`（@Configuration）：注册 `SimpleModule`，对 `Long.class` 与 `Long.TYPE` 添加 `ToStringSerializer`。

- **全局生效**：所有 VO 的 Long 字段（id/runId/userId/total 等）序列化为字符串；前端 TS 类型规则：**一切 id 与 total 均为 string**。
- **审核修正 M4（影响范围补全，前端类型核对清单）**：除 id/total 外，以下 Long 来源字段全部变 string——`PageResponse.total`；B 端仪表盘 `documentCount/pendingChunkCount/knowledgeBaseCount/studentCount/feedbackCount`（DashboardServiceImpl/UserFeedbackServiceImpl 返回 Map<String,Object> 的计数，无编译期保护需人工核对每个 key）；反馈趋势 `count`；`feedbacks/stats` 的 `likedCount/dislikedCount`；`DocumentVO.fileSize`。**以下经后端源码复核为 Integer、保持 number（不适用 Long 铁律，区别于 M4 初稿误列）：文档列表 `chunkCount`、排期 `capacity/enrolled`、`StudentCourseVO.learningCount`**。`page/size`（int）与浮点（rating/score/likeRate/price BigDecimal）不受影响。
- **不受影响**：SSE 事件 payload（worker/entry 手工 toJson，runId 本就是字符串）；SOURCES 事件 score（double）不受影响。
- 既有测试排查：凡断言响应体 JSON 中 Long 数值的快照类测试需同步适配（预计集中在 ApiResponse/Controller 测试的数字断言）。
- 契约文档同步：`docs/contracts/2026-08-16-接口契约定稿.md` 增补「§7 Long 一律字符串序列化」。

### 测试要点

- JacksonConfigTest：Long/long 字段序列化为 `"123"`；Integer 不受影响；LocalDateTime 保持 ISO 格式。
- 既有全量测试回归（`mvn verify`），数字断言适配。

## 二、R1：补口 A——学生会话历史消息接口（设计决策 D2）

### 端点

```
GET /api/v1/student/sessions/{sessionId}/messages?page=1&size=200
权限：hasRole('STUDENT')（复用 StudentController 类级注解）
响应：ApiResponse<PageResponse<StudentMessageVO>>
```

### Controller（StudentController 新增方法，J6/J7 旁）

1. `userId = AuthInterceptor.getCurrentUserId(request)`
2. `sessionService.findById(sessionId)`（selectById 自动过 @TableLogic 软删）→ null 抛 `BizException(NOT_FOUND, "会话不存在")`
3. `!session.userId().equals(userId)` 抛 `BizException(FORBIDDEN, "无权查看此会话")`（会话语义 403，与 ChatStreamEntry 既有先例一致）
4. `messageService.findStudentMessagesBySession(sessionId, page, size)` 包 PageResponse 返回

### 新 VO：`vo/StudentMessageVO.java`（每接口独立，不复用 ChatMessageVO）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | Long（序列化为 string） | 消息雪花 ID（反馈用） |
| role | String | USER / ASSISTANT |
| content | String | 正文（TOOL_CALL/TOOL_RESULT 行为 JSON 串，与实时事件格式一致） |
| messageType | String | null（正文）/ thinking / TOOL_CALL / TOOL_RESULT |
| intentType | String | 意图（依赖 R2 修复；存量行为 null，前端按可空处理） |
| runId | Long | 所属 run |
| seq | Integer | run 内序号 |
| createdAt | LocalDateTime | ISO 字符串 |
| sources | List&lt;RetrievalSource&gt; | **服务端解析后数组**（chunkId/docTitle/headingPath/score），复用 `record/RetrievalSource` 保证前端实时/历史同构；非法 JSON 兜底 `[]` |
| attachments | List&lt;AttachmentRecord&gt; | 用户消息附件（type/url/name/size），复用 `record/AttachmentRecord`；assistant 行恒 `[]` |

### Service：`IChatMessageService.findStudentMessagesBySession(Long, int, int)`

- 实现风格与同文件既有 `findBySessionId` 一致（Wrappers.lambdaQuery + selectPage），但：
  - **投影补 sourcesJson/attachmentsJson 两列**（按需取列）
  - **排序 `createdAt asc, seq asc` 复合**（修复同事务 saveBatch 批内 created_at 相同导致的排序不稳定；run 内唯一性由 V13 (run_id,seq) 唯一索引保证）
  - **M3 处置**：先查会话内 status=COMPLETED 的 runId 列表，消息过滤 `role=USER or run_id in (completedRunIds)`（剔除取消/异常 run 的半截内容，见 §三 M3 段）
  - size 上限 clamp 500
- **M5 同步修复（审核建议，一并交付）**：既有 `findBySessionId`（管理端 H2 回放依赖）排序同样改为 `createdAt asc, seq asc` 复合——同根因（批内 created_at 相同），改动一行，B 端会话回放顺序同步修复；相关既有测试断言同提交适配。

### 转换：`convert/StudentConverter` 扩展

`toStudentMessageVO(ChatMessage)`：`@Mapping(target="sources", source="sourcesJson", qualifiedByName="parseSources")` 等；@Named default 方法用共享 static ObjectMapper 反序列化，空白/异常兜底空列表。**执行注意：改转换器后必须 `mvn clean` 重编**（宪法 MapStruct 条款）。

### 分页评估

选分页（默认 1/200）：一轮工具调用产出 5+ 行（user+thinking+N×TOOL_CALL+N×TOOL_RESULT+assistant），行数不可假设 <100；宪法要求查询必带分页；升序 page=1 即最旧一页，符合聊天 UI 渲染方向。

### 测试要点

- StudentControllerTest：正常映射（含 sources/attachments 解析）/404/403/分页默认值 4 例
- ChatMessageServiceTest：复合排序 + 投影列验证（MybatisPlusTestHelper）
- StudentConverterTest：sourcesJson 合法/非法/null 三态 + attachments 同理（正常/边界/异常）

## 三、R2：补口 B——SSE end 事件补 messageId + intentType 落库修复（设计决策 D3）

### 现状链路（实证）

`doOnComplete`（ChatRequestWorker 525-551）先 `persistMessages`（batchInsert=saveBatch，**返回后实体列表雪花 ID 已回填**）→ 再 `handleCompleted` 构造 END payload `{runId,status}`。**时序天然成立**：落库可拿 ID，END 在其后。metadata 事件在 run 起步即推（assistant 消息不存在），**不可行**。

### 改造

1. 新建 `record/PersistOutcome.java`：`record PersistOutcome(boolean persisted, Long assistantMessageId)`
2. `persistMessages` 返回 boolean→PersistOutcome：
   - batchInsert 后反向扫描**最后一条** role=ASSISTANT 且 messageType==null 的行取 id（最终回答）
   - 幂等跳过分支（DataIntegrityViolationException）→ `PersistOutcome(true, null)`；失败 → `(false, null)`
   - 三个调用点同步改读 `persisted()`，语义不变
3. `handleCompleted(..., Long assistantMessageId)`：END payload 扩为 `{runId, status:"COMPLETED", messageId}`（messageId 恒字符串或 null；null 也显式输出，对齐契约 §2）
4. **CANCELLED/ERROR 终态不带 messageId**（时序上先于落库 + 语义上不反馈半截内容）
5. **顺手修复 intentType**：persistMessages 从 `lastOutput.state().value(OverAllState.KEY_QUERY_PLAN)` 取 `QueryPlan.intent()` 写入 assistant 正文行（修复 intent_type 恒 NULL；存量行仍 null）
6. **PG 回放路径同步**：ChatStreamEntry.reconnect 三处手工构造 end payload（263/295-300/314 行）经新增私有方法 `resolveAssistantMessageId(runId)`（findByRunId 过滤 ASSISTANT+messageType==null 取最后）补 messageId；异常/未落库窗口返回 null（正常降级）。**审核修正 M2**：该方法必须校验 `run.status == COMPLETED` 才返回 id，否则返回 null——与「CANCELLED/ERROR 不带 messageId」语义对齐（取消/异常路径的半截 assistant 行虽已落库，但不得作为反馈目标）。

### M3 处置（审核修正，并入 R1 范围）：历史回显剔除非 COMPLETED run 的半截内容

- **决策**：R1 的 `findStudentMessagesBySession` 查询结果中，**仅保留 USER 行与 COMPLETED run 的非 USER 行**（assistant 正文/thinking/工具行挂靠的 run 非 COMPLETED 时剔除）。
- **理由**：取消/异常路径的半截 assistant 正文已落库，直接回显会出现「历史里一段无标注的半截回答」，与实时对话的「已停止生成」标注语义不一致；剔除后保留 USER 行（用户提问痕迹完整、可续问），体验一致且实现简单。
- **实现**：service 内两步查询（先查该会话 status=COMPLETED 的 runId 列表，再查消息表 `role=USER or run_id in (completedRunIds)`），无 N+1；两步均按需取列。

### 用户消息 messageId

不随 end 下发：前端无即时消费方（反馈只指向 AI 回答；历史回显走 R1 全量）。

### 兼容性

- 前端 `messageId?: string | null`（旧事件/降级无值容忍）
- 契约文档新增 §6：end payload 定稿 `{runId, status, messageId}`；CANCELLED/ERROR 无 messageId；恒字符串

### 测试要点（参照 ChatRequestWorkerTest 反射调 persistMessages 手法）

- persistMessages 返回值三态（有 assistant→id / 无 assistant→null / 幂等跳过→(true,null)）
- doOnComplete：verify bridge.push END payload 含 messageId
- 取消/错误路径 payload 不含非 null messageId
- reconnect 三处补发（ChatStreamEntryTest）
- intentType 落库（mock state 含 queryPlan）
- **旧 boolean 断言测试同提交改造**（宪法：失效旧测试直接删除）

## 四、R3：补口 C——学生会话删除接口（设计决策 D4）

```
DELETE /api/v1/student/sessions/{id}   权限 STUDENT   响应 ApiResponse<Void>
```

1. 归属校验同 R1（404/403）
2. **活跃 run 校验**：`IChatRunService.existsActiveRun(sessionId)`（impl 本表链式 `this.lambdaQuery().eq(sessionId).in(status, QUEUED/ACTIVE).exists()`）→ true 抛 `BizException(CONFLICT, "会话正在对话中，请稍后删除")`
3. 复用 `sessionService.deleteSession(id, userId)`：@Transactional 级联软删 chat_message→chat_run→chat_session（与 H4 管理端同路径，天然级联；@TableLogic 过滤双端不可见）

### 边界（写入方法注释）

- 校验与删除非原子：并发窗口新入队 run 可能被级联软删（频率极低，无数据不一致，不加锁）
- 幂等：重复 DELETE → findById null → 404（REST 语义）
- 前端删除后丢弃本地 runId 并关闭 SSE

### 测试要点

StudentControllerTest 4 例（404/403/409 verify never/正常）+ ChatRunServiceTest（QUEUED/ACTIVE=true、COMPLETED=false）。

## 五、R4：对接契约修订（优化一阶段设计文件）

以下核查结论修订 `docs/design/2026-08-24-双前端整体设计.md` §3（已在设计文件追加「§六 二阶段对接修订」）：

| # | 核查项 | 结论（前端必须遵守的事实） |
|---|---|---|
| 1 | Auth 三端点 | 与设计假设一致：login `{username*,password*,deviceType?}` → `{accessToken,refreshToken,userId,role,displayName}` + Set-Cookie `commerce_token`（httpOnly，Path=/，900s）；refresh body `{refreshToken}`；logout 无 body 幂等 |
| 2 | CORS | 生效白名单 **3000 与 5173**（3001 不生效，B 端必须用 5173）；allowCredentials=true；SSE 跨域直连可用。dev 可改走 proxy（无 CORS） |
| 3 | SSE 帧 | `id:<seq>\nevent:<name>\ndata:<json>\n\n`；事件 9 种命名 + `:heartbeat` 注释行 15s；**未设 X-Accel-Buffering**——经 nginx 反代需 `proxy_buffering off`（dev 直连无影响，部署清单项） |
| 4 | ChatRequest | `{sessionId: Long\|null, query: 必填非空, attachments: [{type,url=objectKey,name,size}]\|null}` |
| 5 | 附件上传 | multipart 字段 `files`（数组）→ `List<AttachmentRecord>`；限额同设计 §1.5.4 |
| 6 | **Long 序列化** | R0 落地后：**前端一切 id/total/size 类 Long 字段按 string 接收**；score/likeRate 等浮点不受影响 |
| 7 | 时间格式 | LocalDateTime → ISO-8601 无时区（`2026-08-24T10:15:30`） |
| 8 | 错误体 | `ApiResponse{code,message,data:null}`；**特例：AuthInterceptor 401 响应无 data 键**（前端类型 `data?`） |
| 9 | PageResponse | `{records, total, page, size}`（total 在 R0 后为 string） |
| 10 | ETL 上传 | multipart：kbId*/title*/courseId?/file*；白名单 pdf/docx/pptx/md/txt ≤100MB |

## 六、宪法合规要点（实施时强制）

1. 新 controller 方法只做参数绑定 + 归属校验（既有先例风格），数据访问全经 service。
2. 新 VO 独立定义；转换一律 MapStruct（StudentConverter 扩展）；**改转换器后 clean 重编**。
3. 新 service 方法接口+impl 成对（I 前缀）；查询按需取列；existsActiveRun 用 exists()。
4. 全部异常 BizException(ErrorCode.XXX)；code=HTTP 同值。
5. 中文注释规范：类/方法/参数/返回值/关键行。
6. R2 persistMessages 返回类型变更导致的旧测试断言，同提交删除/改造（禁过渡）。
7. 新增文件清单：`config/JacksonConfig.java`、`vo/StudentMessageVO.java`、`record/PersistOutcome.java`；修改：StudentController、IChatMessageService/Impl、IChatRunService/Impl、StudentConverter、ChatRequestWorker、ChatStreamEntry；文档：契约定稿增 §6/§7。
